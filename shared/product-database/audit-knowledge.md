# 核销商品数据库与参考图片边界

所有核销 Skill、商品候选检索和新品图片接入的商品身份数据，统一来自 MySQL
`product_catalog.products`。唯一读取入口为 `audit_core.product_database.load_product_catalog`。
正式表结构见 [schema.sql](schema.sql)，部署和迁移见 [README.md](README.md)。

## 数据库事实

- `product_code`：区分大小写的准确商品编码，主键。
- `barcode_69`：完整、有效且以 69 开头的 EAN-13；同一条码可以有多个商品编码。
- `product_name`：数据库中的商品名称。用户2026-09-22进一步确认允许简称，不要求逐字相同；以本次资料能唯一对应为准。优先产品编码或名称加69码；仅一个已有标识也能唯一确定时不强制补另一字段。名称简称由AI结合轻量身份信息确认，保留规格、款式及组合装的区别；多个可能或明确冲突不猜选、不取候选图片。
- `image_manifest_key`：可空的商品图片集元数据，存储已验证 OSS 多视图清单的稳定 Object Key，
  不是商品身份字段，不存临时签名 URL。与三个身份字段在同一只读事务读取；
  图片关联元数据使用独立哈希，不改变原三个身份字段的哈希定义。NULL 表示未登记图片集。

OSS 商品参考图采用固定路径覆盖策略，不做图片版本管理：
`offline-verify/product-reference/<product_code>/manifest.json` 指向同目录多视图；同视图更新覆盖原对象，
不创建版本目录或应用侧历史图片副本。新图片经完整性校验后再更新清单；
读取时必须核验清单内的 SHA-256，更新期间不一致则重新读取清单并有限重试，不能跳过校验。
同任务只复用已校验临时副本，结束后清理；下一任务取最新图片。
断电或强制中断留下的已登记临时副本，由下一次正式 runner 启动时检查占用锁及归属后补清理。
正在使用、含链接或暂时无法删除时保留到后续运行重试；此机制不删除 OSS 原图、原始 ZIP 或正式核销档案。
历史记录中的对象路径及哈希不等于旧图片仍可恢复。此约定不改变核销档案或原始业务 ZIP 的留存，
唯一图片配置位于 `product-images.json`；配置缺失、损坏或不是已批准的 OSS 范围时必须报错。
所有正式代码、Skill、新品维护和评测均无本地图库入口；GitHub 灾备完全独立，不提供运行回退。

当前数据库没有商品编码别名、历史名称、独立规格/香型字段。不得从旧 JSON、目录名称、
参考图片的文字说明、历史结果或外部接口填充这些字段。`SP-1` 等短码只有在数据库的名称或
准确编码字段中实际存在时才能参与对应；它不能凭历史记忆被当作已登记的编码别名。

同次正式运行在第一次需要商品知识时查询一次，使用一致的只读事务快照完成候选检索和核销，
在当前PDF流程的技术观察记录中保存数据库条数、读取时间、内容哈希、所选商品及取图范围；历史入口保留其 `analysis/product-database.json` 路径。
下次运行重新查询，不复用上次快照。只读账号通过 TLS 连接，凭据留在容器秘密文件中。
连接失败、空表、非法身份或读取不完整属于系统错误，停止核销，不转成客户材料错误。

## 当前核销与现场商品对照（2026-09-22用户确认）

当前正式核销执行本类型审核栏与已确认补充。用户2026-09-22最终确认：所有POS数据以Excel为准，只必含5+2项；商品名称允许模糊匹配，结合69码须唯一对应，69码须与库内一致。POS额外产品编码及其他列不审核，缺失、归属不明或与我方不一致均不报问题，也不用它筛选商品。此口径覆盖此前填写编码须一致的要求。POS身份核对只查轻量名称、69码及库内唯一商品身份，不读OSS清单或图片；现场商品外观仍按本次合同范围另行取图。不恢复旧人员奖励资格、旧陈列合同逐行主账检查或EAN校验位审核。

用户2026-09-22确认：所有已有的现场照片对应SKU检查共用按需取图流程。先从品牌方本次合同、产品推广协议及其申请说明确定本次需核对的商品；优先用明确的产品编码，或用产品名称加69码共同锁定数据库中唯一产品编码。用户同日进一步确认：商品名称允许简称，不要求逐字相同；只要本次资料能确定唯一对应商品即可，不强制补齐另一标识字段。用库内轻量身份信息核对名称含义，保留规格、款式和组合装等区别；有多个可能商品或明确冲突时不能猜选。多个标识冲突、同名同码仍对应多个编码或资料无法唯一定位时，说明具体参照缺口，不扩大候选下载。用户同日进一步确认：本次商品在库内未找到时，结果直接写‘库内无参考商品’，保留对应商品名称或编码。只说明这个情况，不写成客户缺交照片、商品未上架或商品不合格；继续其他检查，不据此决定是否核销。锁定商品并按编码去重后，只读取这些商品的数据库OSS清单和对应细节图，禁止每次下载整库上千张图片再找商品，也不能先遍历全部OSS图片清单或按品牌批量取图。同一核销单跨门店、跨照片复用已验证的同一商品图片。参考图仅用于辨认产品外观；现场是否出现及是否清晰可见，必须由本次实际照片证明，不能把合同列有商品或参考图清晰当成现场已出现，不能据参考图补写模糊的现场文字。不强制现场拍清条码数字，照片取图本身不新增商品字段必交或EAN校验位审核；POS商品库一致性按另行确认的通用规则执行。仅在本类已有照片商品检查范围使用；仅检查照片有无、品牌、水印、价格等时不追加全部SKU覆盖要求，外采赠品不强制属于我方商品库。参考图缺失不是客户缺交资料；技术连接、完整性或认证故障按系统错误处理。

具体流程见[现场商品按需对照图片](../../skills/orchestrate-offline-audit/references/product-photo-reference.md)。程序先从本次品牌方合同/协议及申请说明提取商品清单，再以准确产品编码，或名称加69码定位唯一编码；名称允许简称，以能唯一对应为准。不可先从整库图片找相似外观，也不强制现场能拍清条码数字。

只有唯一定位并去重后的商品行才能调用 `attach_product_reference_images`；未选中商品的OSS清单都不读取。只下载这些商品关联的细节视图，同一图片字节在本单复用，不能按门店或照片重复下载。不截断本次应核对商品清单以伪造全量完成。缺图不等于未登记，外采赠品不强制登记我方商品库。

参考图与现场照片一起交给隔离模型，判断清晰可见的包装、规格和款式。品牌、颜色、盒型或背景不能单独确立SKU；合同选择待对照商品，但不能证明现场已经出现或升级模糊照片的识别结果。每条现场依据须指向本次照片，不复制参考图文字到现场事实。

参考图片仅支持外观，不证明门店、日期、陈列数量/面积、活动价格、促销、照片原创性或金额。私有认证由宿主负责，模型不接触密钥或下载地址。沿用OSS路径、身份、类型、尺寸、大小和SHA-256校验及任务临时缓存；成功或异常退出均清理，清单更新时不混用新旧图片。

## 新品和维护

新增或更正主数据在数据库维护流程完成。核销及新品图片接入的只读查询不写数据库，
也不因旧 JSON 中出现商品就认为数据库已经登记。
新品图片接入先独立观察包装，再从数据库同码候选中唯一选定商品；预演及应用前重新查库核对
选中的三字段。只在授权的图片写入范围内维护 OSS 参考图片、清单及数据库图片关联。
原始素材集合和历史档案保留；登记图片经迁移校验后只在 OSS 保存。本地图库维护入口已移除，
新图片必须先经身份确认与写入授权，再按固定 Object Key 上传、校验、发布清单。此边界不授予自动上传任意素材的权限。
