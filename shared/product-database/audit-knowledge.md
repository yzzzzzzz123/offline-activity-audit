# 核销商品数据库与参考图片边界

所有核销 Skill、商品候选检索和新品图片接入的商品身份数据，统一来自 MySQL
`product_catalog.products`。唯一读取入口为 `audit_core.product_database.load_product_catalog`。
正式表结构见 [schema.sql](schema.sql)，部署和迁移见 [README.md](README.md)。

## 数据库事实

- `product_code`：区分大小写的准确商品编码，主键。
- `barcode_69`：完整、有效且以 69 开头的 EAN-13；同一条码可以有多个商品编码。
- `product_name`：数据库中的完整商品名称。名称采用唯一模糊相容，不要求逐字相同；
  规格、款式及组合装文字仅在该名称本身含有时可作检索线索。
- `image_manifest_key`：可空的商品图片集元数据，存储已验证 OSS 多视图清单的稳定 Object Key，
  不是商品身份字段，不存临时签名 URL。与三个身份字段在同一只读事务读取；
  图片关联元数据使用独立哈希，不改变原三个身份字段的哈希定义。NULL 表示未登记图片集。

OSS 商品参考图采用固定路径覆盖策略，不做图片版本管理：
`offline-verify/product-reference/<product_code>/manifest.json` 指向同目录多视图；同视图更新覆盖原对象，
不创建版本目录或应用侧历史图片副本。新图片经完整性校验后再更新清单；
读取时必须核验清单内的 SHA-256，更新期间不一致则重新读取清单并有限重试，不能跳过校验。
同任务只复用已校验临时副本，结束后清理；下一任务取最新图片。
断电或强制中断留下的已登记临时副本，由下一次正式 runner 启动时检查占用锁及归属后补清理。
正在使用、含链接或暂时无法删除时保留到后续运行重试；此机制不删除 OSS 原图、原始 ZIP 或正式核销档案。
历史记录中的对象路径及哈希不等于旧图片仍可恢复。此约定不改变核销档案或原始业务 ZIP 的留存，
唯一图片配置位于 `product-images.json`；配置缺失、损坏或不是已批准的 OSS 范围时必须报错。
所有正式代码、Skill、新品维护和评测均无本地图库入口；GitHub 灾备完全独立，不提供运行回退。

当前数据库没有商品编码别名、历史名称、独立规格/香型字段。不得从旧 JSON、目录名称、
参考图片的文字说明、历史结果或外部接口填充这些字段。`SP-1` 等短码只有在数据库的名称或
准确编码字段中实际存在时才能参与对应；它不能凭历史记忆被当作已登记的编码别名。

同次正式运行在第一次需要商品知识时查询一次，使用一致的只读事务快照完成候选检索和核销，
在技术档案 `analysis/product-database.json` 记录实际数据、条数、读取时间和内容哈希。
下次运行重新查询，不复用上次快照。只读账号通过 TLS 连接，凭据留在容器秘密文件中。
连接失败、空表、非法身份或读取不完整属于系统错误，停止核销，不转成客户材料错误。

## 业务对账

人员激励：Excel 销售 SKU 先按准确有效的 69 码筛选数据库记录，再用原始商品名称作唯一模糊
消歧；选中记录的编码只用于追溯。未唯一匹配前该 SKU 不支持奖励。人员视觉步骤只看结算及
转账图片，无须访问商品参考图片。

促销堆头：合同核心具体商品和合同附件逐行商品分别核对数据库。来源同时提供编码和 69 码时，
两者必须命中同一数据库行；数据库没有登记的编码不能由旧 JSON 别名放行。
严格标识及独立交易事实唯一定位业务行后，名称不同、缺失或不可读不单独产生名称差异。
核心合同、附件、照片和独立销售 Excel 的原有权威关系继续执行：销售 Excel 直接对合同附件，
不增加 Excel 到数据库或照片到 Excel 的跨来源关联。

其他核销场景按自身规则检查原始业务材料；需要商品知识时只用此数据库入口。
本次数据源变更不为原本没有商品主账门槛的场景新增核销条件，也不把合同、金额或现场事实改成数据库事实。

## 现场商品与参考图片

1. 从同一现场照片提取真正可见的名称片段、编码、条码、规格、款式和组合装文字。
2. 仅用这些可见文字检索完整数据库；每张照片最多 4 个候选，每店任务最多 8 个候选。
   候选筛选发生在取图之前，不能因 `views` 尚未加载而排除数据库商品；图片集为空也不等于商品不存在。
3. 需要视觉比对时，调用 `audit_core.product_images.attach_product_reference_images`，
   从候选数据库行的 `image_manifest_key` 读取私有 OSS 清单，严格核对准确商品编码加 69 码、
   同商品授权前缀、视图 ID、类型、大小、尺寸和 SHA-256。不读取本地图片索引或任何灾备资料。
4. 只把选中的图片下载到任务临时目录，每商品最多附加 4 张参考图；校验完整字节、SHA-256、图片解码与尺寸，
   再交给隔离模型。任务内复用已验证副本，成功或异常退出清理。图片更新期间最多重读一次；清单变化时停止，不能混用新旧图。
   私有认证由宿主负责，模型不接触密钥或下载地址。缺图不影响数据库商品存在性，
   但不能形成照片商品的完全视觉命中；路径越界、图片损坏或哈希异常属于系统故障。
5. 提交照片中的有用文字唯一支持某个数据库商品，且包装与所附参考图整体相容时，才返回
   `exact`；存在多个可能身份时为 `candidate`；没有可靠对应时不返回命中。

允许角度、距离、光线、遮挡、姿态存在正常差异，只要包装主要色块、版式和组合结构相容且无
可见冲突。品牌、颜色、盒型、通用卖点、二维码、批号或背景不能单独确立 SKU。
数据库及参考图内容都不能冒充现场可见文字；合同和 Excel 不能选择或升级照片商品。
商品身份确认后，再独立核对其是否属于合同范围。

参考图片只支持包装身份，不能证明现场门店、地点、日期、陈列数量/面积、活动价格、促销、
照片原创性或金额。每条视觉依据都须指向提交现场照片中实际可见的内容。

## 新品和维护

新增或更正主数据在数据库维护流程完成。核销及新品图片接入的只读查询不写数据库，
也不因旧 JSON 中出现商品就认为数据库已经登记。
新品图片接入先独立观察包装，再从数据库同码候选中唯一选定商品；预演及应用前重新查库核对
选中的三字段。只在授权的图片写入范围内维护 OSS 参考图片、清单及数据库图片关联。
原始素材集合和历史档案保留；登记图片经迁移校验后只在 OSS 保存。本地图库维护入口已移除，
新图片必须先经身份确认与写入授权，再按固定 Object Key 上传、校验、发布清单。此边界不授予自动上传任意素材的权限。
