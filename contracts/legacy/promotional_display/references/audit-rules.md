# 促销堆头确定性规则

## 判定顺序

商品知识库统一指 MySQL `product_catalog.products`，按[数据库知识规则](../../../shared/product-database/audit-knowledge.md)
读取本次只读快照。候选参考图片只按数据库 image_manifest_key 从私有 OSS 查询，缺失配置或读取失败时停止，不回退。核销顺序固定如下：

1. 合同核心六项必核控制；
2. 核心合同中的具体商品，以及合同附件中的每个商品 → 商品知识库；
3. 现场照片可见文字 → 完整且已校验的商品知识库，再将现场包装 → 已检索参考图片；随后单独比较已识别商品是否属于合同范围；
4. 销售 Excel 内部算术，再以合同附件为基准，对销售 Excel 比较八个检查字段；单位只保留展示，不参与判定；
5. 按明确费用口径计算金额并作出最终结论。

任何金额、文件名、销售行或通用名称相似性，都不能绕过未通过的合同商品或照片商品检查。
销售 Excel 绝不提供目录身份，也绝不参与照片身份识别。销售差异必须以合同附件为基准报告，不能改写合同事实。

## 合同提取与解释

- 保留所有可见签约主体。`customer_name` 是预计出现在销售文件中的客户/经销商，只能从合同文字中选择。
- 保留活动预算、执行期间、活动内容、逐字的核销/结算方式、陈列标准、申报金额、所列经销商/门店、堆头总数、每店堆头数、水印和印章。合同水印可见性只作信息展示，绝不参与核销。
- 对每页印刷密集的附件，完整合同提取后，必须使用 `contract-product-cells.schema.json`，以原始分辨率聚焦重读每一行的商品编码、商品名称和 69 码单元格。保持相同的行/页顺序。第一次提取的交易数值可用于定位行，但销售 Excel 和商品知识库都不得提供、更正或暗示重读身份字段。数字单元格清晰而旁边编码、名称或 69 码似乎缺失时，必须再次聚焦读取；第一次 OCR 遗漏不能证明 PDF 单元格为空。每个非空的重读 69 码都必须通过 EAN-13 校验。
- 费用措辞必须严格分类：
  - `per_store`：明确说明每家所列门店的单位费用；
  - `per_stack`：明确说明每个堆头/陈列单元的单位费用；
  - `total_only`：只有总预算或总申报，没有单位分配依据；
  - `unclear`：无法确定单位口径。
- 绝不能通过总额相除推断单位费用。
- 只有合同明确给出，或明确规定每家所列门店一个堆头时，才设置门店的 `stack_count`。
- 全品牌、全系列、宽泛品类、活动措辞或附加销售/商品表，不属于狭义合同 SKU 条件。
- 只有核心合同条款给出具体编码、足够具体的商品名称或完整有效的 69 码时，才设置 `requires_specific_products=true`。
- 只有核心条款明确要求促销机制时，才设置 `requires_promotion=true`。

## 合同商品 → 商品知识库

商品知识库只对商品身份具有权威性。以下两类合同侧来源必须分别对账：

- 核心合同条款强制要求的具体商品身份；
- 印刷版合同销售附件中的每一行。

所有已提供的身份字段都必须保留。已提供的 69 码必须是完全有效的 EAN-13，并与目录条码一致。
来源内部的业务商品编码必须保留，用于合同附件与销售 Excel 的严格比较。执行商品 → 知识库对账时，
该编码必须与数据库 `product_code` 完全一致；当前表无编码别名，旧 JSON 别名不能放行。
商品编码与 69 码必须共同识别同一数据库记录。

商品名称文字只是模糊辅助证据，绝不要求逐字相同。可比的业务商品编码与 69 码一致后，不得因名称写法不同、缺失或不可读，
另外生成商品名称不一致或让该行失败。严格标识与独立交易事实唯一定位该行后，不可用的名称只能记录为辅助信息，
不得计入问题或补交项。包装短码仅在数据库名称或准确编码中确实存在时作为模糊文字锚点，绝不能由旧图片索引的别名替代严格商品编码字段。
`matched` 和 `fuzzy_matched` 均通过；歧义、冲突、缺失、无效或未登记的身份，会使对应的合同侧行失败。
附件行始终只是销售证据，绝不能变成核心商品或促销要求。

当一组完全一致的商品编码与 69 码对应多个目录变体时，使用合同附件中模糊相容的商品名称消歧。
如果原 PDF 单元格肉眼可见有文字，而名称被返回为 null，应判为合同 PDF 提取失败并重读单元格；
不得称为来源商品编码与知识库不一致。

## 销售 Excel → 合同附件

直接从源单元格读取每条销售行，并保留：

- Excel 行号；
- 客户与业务日期；
- 原始商品编码、商品名称与 69 码；
- 存在时的单位、数量、零售价和总金额。

AI 证据不包含销售身份，不能覆盖这些值。

先检查 Excel 内部：每行的数量 × 零售价必须等于该行总金额，任何印刷总计也必须与明细行一致。
随后将每条合同附件行最多配对一个尚未使用的 Excel 行，并比较八个字段：客户名称、业务日期、商品编码、商品名称、69 码、数量、零售价和总金额。
合同值是比较基准。编码、条码、数量、价格和金额严格比较；客户名称保持保守模糊匹配；商品名称只是辅助模糊文字，
严格标识与交易事实已定位该行后，名称不得单独产生差异、缺失名称失败、问题数量或补交要求；日期允许语义等价格式。

保留双方原始单位值用于展示，但单位不参与配对、字段结果、通过/不通过、置信度、问题数量、核销金额或补交要求。
保留 PDF 页码、附件行号、Excel 行号、每个检查字段状态、合同各行算术及印刷总计。
未配对的合同或 Excel 行必须可见，并阻止自动核销。

不得把独立销售 Excel 与商品知识库对账。不得将其与现场照片比较，也不得用其识别或升级照片商品。
若合同没有逐行销售附件，则每条 Excel 行都缺少合同基准：返回 `unverifiable`，列出这些行，要求补交完整合同附件，
不得退回使用商品知识库或照片替代。

## 合同商品 ↔ 商品知识库

- `not_applicable`：核心合同没有可核验的具体商品身份；
- `pass`：每个具体合同身份都通过明确字段唯一映射；只允许保守模糊名称匹配，且已提供的严格字段必须保持一致；
- `fail`：合同提供的编码/名称/条码在目录中缺失、存在歧义或发生冲突。

此项适用时，每个必需的核心合同商品 ID 都必须出现在现场照片的完全命中中。
销售 Excel 不属于这个商品身份门槛。

## 现场照片 ↔ 商品知识库

现场商品身份必须独立于合同及销售商品文字解析：

1. 从每张提交照片提取有用的可见文字与身份锚点；
2. 只用同一张照片的文字，从完整且已校验的目录中检索小型候选集；
3. 将文字与目录控制的名称、别名、规格、变体和包装文字对应，再把提交包装与已登记参考视图比较；
4. 返回完全命中、候选或未命中身份。

商品名称、编码和条码由数据库控制，参考视图 ID 和 Object Key 只由数据库关联的 OSS 清单提供，模型文字不得改写。

- `exact`：可见文字唯一对应一个目录商品，并且提交包装与至少一个已登记多视图参考图片在整体视觉上相容。文字路径可以是数据库名称或准确编码中存在的唯一可见文字、完整有效的可见 69 码，或由部分名称、规格、口味/变体、组合标记与包装文字唯一收敛的其他组合；例如 `3+2` + `420g` + `量贩装` 可检索到已登记的 `3+2` 组合装。无须看到完整商品名称或 69 码。视觉相容不要求像素相等：只要核心色块、布局、组合结构和可识别特征一致且没有冲突，即允许透视、距离、光线、货架遮挡及包装姿态差异；
- `candidate`：包装或模糊名称文字相容，但商品不唯一；多个数据库记录共享的文字在出现其他可见消歧事实之前都保持候选；
- `unmatched`：没有目录商品得到支持。

当至少存在一个商品，且文字加参考图片链返回的每个命中都是完全命中时，`现场商品知识库` 控制通过。
合同归属是另一项独立控制：身份固定后，每个完全命中都必须满足适用的合同商品范围。
因此，现场商品可以通过知识库身份检查，但仍在 `现场商品与合同` 中失败。
模糊结果绝不能因为合同或 Excel 中出现同一商品就升级为完全命中。
没有相应现场文字时，品牌、颜色、形状、通用卖点、二维码、批号/日期喷码、背景或视觉相似性都不能确立商品身份。

## 有方向的对账

### 合同 ↔ 销售

- 对客户/公司后缀做保守规范化后，将每个销售客户与合同客户/主体比较。完全相同或唯一模糊实体对应则通过；不一致则失败；证据缺失则无法核验。
- 解析每个销售业务日期或年月。每个解析出的区间都必须完全被合同执行期间覆盖。超期失败；缺失/不可解析则无法核验。
- 印章是必核完整性控制：肉眼可见缺失则失败，无法核验则不能自动通过。水印只可单独作为信息事实报告；水印缺失或无法核验绝不改变状态、置信度、金额或补交要求。
- 任何不一致都会使全局对账失败；任何必核项无法核验都阻止自动通过。

### 合同 ↔ 现场照片

每家门店比较：

- 已提交照片；
- 完整可见日期位于合同期间内；
- 可见地点与合同经销商/门店对应；
- 陈列证据证明要求的“或”分支；
- 合同要求促销时，有明确促销可见；
- 适用时，存在合同要求的具体商品。

schema 保留 `exact`、`compatible`、旧版 `mismatch`、`location_unverified` 和 `filename_only`。
可见合同名称完全对应时，无须调用地图，且不存在地点置信度问题。其他所有可辨认的名称差异（包括编号分店缺口）
都必须先通过固定百度地图 Streamable HTTP MCP 解析器调用 `map_search_places`。
从当前进程的 `BAIDU_MAPS_API_KEY`，或 Windows 当前用户环境配置读取服务端 AK；绝不能从仓库文件或命令行参数读取，
也绝不能暴露带认证的 URL。用户级配置应让日常核销无需另开交互终端即可直接运行。

持久化保存解析服务方、是否尝试 MCP、双方查询、选定 POI/地址/`BD09LL` 坐标、直线距离、阈值、`confidence`、证据及中文依据。
选中同一 POI、已验证属于同一建筑的商场/门店父子关系，或选中 POI 相距不超过 100 米时，`confidence=high` 并变为 `compatible`。
不要求双方都独立唯一：保留任何可信唯一的一方；每个未解决方的候选必须达到内部 0.60 名称相关性阈值；
若双方都不具备可信唯一性，则双方都必须达到阈值；只有最佳合格候选对构成上述任一空间通过关系时才接受。

其他所有解析结果——包括远距离唯一候选对、100 至 300 米灰区、没有可信候选对、MCP 不可用或缺少可比坐标——
均为 `confidence=low`，变为 `location_unverified`，人工解决前支持金额为零，并展示为 `门店地点低置信度`，
不得自动展示为 `门店水印错误`。远距离结果必须保留实测距离，并要求补交权威同址/邻近证据或地点正确的照片。
绝不能在面向客户的输出中暴露内部相关性分数。新判定不得输出 `mismatch`；仅为兼容旧快照保留读取能力。
MCP 不可用或结论不明确时，schema 校验通过的地点登记表可以解析对应关系；MCP 与登记表冲突时仍保持低置信度/人工处理。
`filename_only` 表示水印地点缺失或不可读。文件名绝不是地点证据，也绝不能升级或覆盖任何解析结果。

### 禁止的跨来源关联

- 现场照片不与销售 Excel 比较，因为提交的 Excel 没有权威门店列，也不是视觉执行的合同基准。
- 销售 Excel 不与商品知识库比较；其商品字段直接与相应合同附件行比较。
- Excel 值绝不能选择照片候选、消除照片歧义或改写合同值。

## 陈列标准

陈列规则为“或”条件：

- `stack_1sqm`：提交视图提供可见比例、尺寸或完整占地证据，可证明约一平方米；
- `four_vertical`：同一陈列从左到右至少有四个不同的实体列/排面同时可见、可数；透视压缩或部分侧向的边缘堆叠，只有在相邻正面列以外存在边界独立、重复成列的额外包装时才计数；
- `both`：两个分支均得到证明。

`standard_evidence=meets` 只能搭配 `stack_1sqm`、`four_vertical` 或 `both`；
`does_not_meet` 只能搭配 `none`；`unclear` 只能搭配 `unclear`。

同品牌下不同 SKU、组合装和包装形式可以共同组成四列；不要求同一 SKU 出现四份，但明显属于其他品牌的相邻商品不得计数。
多张已路由照片分别评估：任意一张可以证明四列，但绝不能把多张照片的部分数量相加。
已经计数的正面包装，其暴露侧面不得再次算作另一个排面，即便该侧面在多个货架层重复出现。
三个正面箱旁紧贴的一排狭窄侧面仍算三列，除非包装接缝、错位或另一个独立正面能够证明单独堆叠。
不得累加竖向叠放的箱子，不得跨货架层重复计算同一摆位，不得合并独立背景货架，也不得推断完全隐藏的列。
边缘堆叠即使倾斜，只要边界独立也不得忽略。泛泛的 `陈列符合` 不是可见依据。

只有不可变合同门店和所有按路由顺序排列的照片 SHA-256，都与已接受的视觉回归登记项完全一致时，
登记表才可替换聚焦观察。任一字节、照片集合、顺序或门店路由变化都会使校准失效。
替换后记录校准 ID 并执行相同的结构化陈列校验；绝不能按文件名或视觉相似性匹配。

## 照片复用

确定性代码在提交的现场照片之间计算完全一致和感知图片指纹：

- 跨门店字节完全一致的复用失败；
- 尚未解决的跨门店近似图片复用候选会阻止自动通过；
- 未发现问题时，只通过复用控制本身。

复用证据保留在 JSON 中。工作簿只展示 `未发现`、`发现`、`疑似` 或 `无法判断`，绝不展示原始哈希或成对计算。
照片复用与陈列合规相互独立。

## 促销

促销必须有明确可见信号：特价措辞、原价/现价、折扣、赠品、多件购、`1+1`、`3+2` 或量贩装措辞。
普通价签不属于促销。可见性不足时返回 `无法判断` 并说明限制。

## 金额与最终门店控制

每家门店要获得自动支持，必须通过所有适用控制：

- 合同 ↔ 销售全局对账通过；
- 合同核心六项必核控制全部通过；
- 可选合同商品知识库检查通过；
- 存在合同附件时，其商品知识库检查通过；
- 已提交照片并绑定到正确门店；
- 可见日期和地点通过；
- 陈列通过；
- 照片复用通过；
- 照片知识库身份为完全命中，且单独识别的照片商品满足适用合同范围；
- 合同要求时，明确促销通过；
- 合同附件 → 销售 Excel 八字段对账通过；单位只作展示；
- 销售 Excel 内部算术通过；
- 金额具有明确单位口径。

金额计算：

- `per_store`：每家通过门店按 `1 × 单位费用`；
- `per_stack`：每家通过门店按 `明确的门店堆头数 × 单位费用`；
- `total_only` 或 `unclear`：自动分配为零，需人工确认；
- 最终建议金额不得超过支持金额、申报金额及明确活动预算（如有）中的最小值。

缺失、不一致、不确定、模糊、重复或需人工分配的控制，在解决前支持金额为零。

## 内部工作簿与客户文案

内部六列结果保留完整证据和核销判断，供验证与技术审计；以下逐项比较、通过事实、置信度、结论及操作不是客户错误原因的拼接模板：

1. 合同；
2. 现场照片；
3. 销售 Excel；
4. 与合同进行的有方向比较；
5. 金额；
6. 结论及不超过三条后续操作。

按以下顺序渲染：合同核心六项控制；合同商品知识库；合同附件摘要及每组附件/Excel 配对的一条明细行
（另加未配对 Excel 行）；门店/照片行；最终金额。不得暴露候选集、完全/感知哈希或完整模型推理。
输出必须可供阅读者独立使用：绝不能写 `详见审计JSON`、`见内部结果` 或引用其他无法取得的文件。
