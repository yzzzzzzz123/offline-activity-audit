# 线下市场费用核销 AI 技术方案

**适用场景：地堆/陈列、人员激励**  
**文档版本：V1.0（客户同步版）**  
**编制日期：2026 年 8 月 14 日**  
**文档属性：纯技术方案，不含商务报价**

---

## 1. 方案摘要

本方案建设一套以“证据结构化、确定性规则核验、Agent 受控判断、人工最终审批”为核心的线下市场费用核销系统，覆盖地堆/陈列与人员激励两类业务。

系统接收图片、PDF、Excel/CSV 及压缩包后，依次完成材料归集、文件分类、OCR/视觉识别、证据标准化、跨材料勾稽、金额重算、风险判断、补件提示、人工复核及结果回写。所有关键字段和判断必须保留原始文件、页码/工作表/行号、坐标区域、文件哈希、识别版本和规则版本，确保结论可解释、可复核、可追溯。

核心技术原则如下：

1. **模型负责识别事实，不直接计算可核销金额。** OCR/视觉模型只输出结构化证据及置信度。
2. **金额、日期、数量、门店和材料完整性由确定性程序判断。** 规则引擎完成逐 SKU、逐门店及逐笔支付勾稽。
3. **Agent 负责最终建议与解释，但必须经过 Decision Guard 校验。** Agent 不能覆盖硬规则、不能抬高程序计算的支持金额。
4. **缺证、低置信度或证据冲突不得自动通过。** 统一进入“待补件”或“人工复核”。
5. **总金额相同不等于证据链完整。** 必须同时验证材料类型、主体、期间、明细、签章、支付来源和唯一性。
6. **真实性能力按证据边界表述。** 水印、文件哈希和感知哈希只能提供一致性或重复风险线索，不能单独证明现场真实或文件未被篡改。

## 2. 建设范围与技术边界

### 2.1 建设范围

- 对接勤策核销单、钉钉群机器人或 H5 上传入口。
- 支持单个核销单独立提交，也支持批量导入历史核销包。
- 支持地堆/陈列、人员激励两个场景的材料自动分类。
- 支持结算单、促销合同、盖章 POS、POS 电子表、红包/工资打款截图、微信批量导出明细、现场照片的识别与校验。
- 支持统一结算单模板识别、客户印章可见性检测、合同签章检测和电子签名校验。
- 支持逐门店、逐 SKU、逐笔支付的证据链与核销金额计算。
- 支持结果 Excel/JSON、H5 复核任务、补件清单、审计日志及勤策状态回写。

### 2.2 技术边界

- 图片中“可见印章”只代表检测到印章图像，不等同于司法或公安意义上的印章真伪鉴定。
- 无可信 EXIF/GPS、可信时间戳或平台定位记录时，画面水印只能作为可见信息，不能单独证明拍摄时空真实性。
- pHash/dHash/图像向量用于筛查完全重复或近似复用候选，不作为像素级篡改鉴定结论。
- 二维照片无法可靠测量真实面积。合同要求“1 平方米或 4 纵陈列”时，系统可识别可见纵列；面积要求若缺少尺度参照，应输出“不确定”并转人工。
- 只有聊天截图、无交易单号/完整日期/付款主体时，只能证明画面存在相应金额卡片，不能证明完整发放链路。
- AI 输出为审核建议，资金审批和最终付款仍由授权人员完成。

## 3. 审核标准结构化

系统不采用不可解释的综合打分替代硬规则。每条规则输出 `PASS`、`FAIL`、`UNKNOWN` 或 `NOT_APPLICABLE`，并携带证据引用、金额影响和补件要求。

### 3.1 地堆/陈列核销规则

| 规则 ID | 核验对象 | 技术核验方式 | 未通过处理 |
|---|---|---|---|
| GD-MAT-001 | 活动照片存在 | 材料分类 + 文件清单 | 全局待补件或对应门店不支持 |
| GD-WM-001 | 照片可见日期、地址、拍摄时间水印 | 水印区域检测 + OCR + 日期/地址解析 | 对应门店待补件 |
| GD-TIME-001 | 水印日期在合同活动期间内 | 规范化日期与合同起止日闭区间比较 | 对应门店不支持，人工复核 |
| GD-STORE-001 | 水印地点/门店与合同门店一致 | 门店主数据、地址、经确认别名映射 | 未映射时不得由模型猜测 |
| GD-SCENE-001 | 清晰展示堆头/陈列全貌 | 画面完整度、遮挡、模糊、裁切检测 | 对应门店待补件 |
| GD-PRODUCT-001 | 活动产品摆放可见 | 商品/品牌识别 + 证据框 | 对应门店待补件或不支持 |
| GD-PROMO-001 | 促销标识可见 | 价签、促销牌、物料检测 | 按合同硬性要求处理 |
| GD-STANDARD-001 | 达到约定陈列标准 | 纵列计数、堆头/货架分类、可见尺度判断 | 不确定时转人工，不自动通过 |
| GD-DUP-001 | 未重复使用照片 | SHA-256 + pHash/dHash + 图像向量 + 历史指纹库 | 精确重复阻断；近似重复人工并排复核 |
| GD-SET-001 | 公司统一模板结算单存在 | 文档分类 + 模板注册表匹配 | 全局待补件，全部金额暂缓 |
| GD-SET-002 | 结算单有客户盖章 | 印章检测 + 印章文字 OCR + 客户主体比对 | 全局待补件/人工复核 |
| GD-CON-001 | 签章促销合同存在 | PDF/图片分类、签章可见性、电子签名验证 | 全局待补件，全部金额暂缓 |
| GD-CON-002 | 合同期间、门店、标准、单价完整 | 合同 OCR/表格结构化 | 无法确定规则时整单人工复核 |
| GD-AMT-001 | 结算金额与逐店支持金额一致 | 程序计算 `Σ合格门店费用` | 超报部分暂缓，不允许 Agent 覆盖 |

地堆支持金额按门店计算：

```text
store_supported_amount =
  fee_per_store，若该门店所有强制规则均为 PASS；
  0，若任一强制规则为 FAIL 或 UNKNOWN。

case_supported_amount = min(
  claimed_amount,
  settlement_amount,
  Σ store_supported_amount
)
```

若统一结算单或签章合同等全局材料缺失，即使部分门店照片通过，也只记录“潜在支持金额”，整单建议金额暂置为 0，状态为 `NEED_SUPPLEMENT`。补件后可复用已完成的逐店识别结果，无需全部重跑。

### 3.2 人员激励核销规则

| 规则 ID | 核验对象 | 技术核验方式 | 未通过处理 |
|---|---|---|---|
| PI-POS-001 | POS 电子表存在且可读取 | 原生 Excel/CSV 解析，不对电子表截图做 OCR | 全局待补件 |
| PI-POS-002 | 经销商盖章 POS 存在 | 盖章 PDF/图片分类、印章检测与主体比对 | 全局待补件 |
| PI-POS-003 | 盖章 POS 与电子表一致 | 门店、SKU、数量、金额汇总勾稽 | 冲突时人工复核 |
| PI-TIME-001 | POS 销售发生在活动期间 | 逐行日期解析与活动期间比较 | 期外行剔除并列明金额影响 |
| PI-SKU-001 | 结算 SKU 与 POS SKU 唯一映射 | 条码优先；商品主数据次之 | 模糊映射不得自动通过 |
| PI-QTY-001 | 结算数量与 POS 数量一致 | 逐 SKU、逐门店程序汇总 | 按较低的已证实数量计算 |
| PI-RATE-001 | 奖励单价符合合同 | 合同条款结构化 + 行级计算 | 不一致行暂缓 |
| PI-SET-001 | 统一模板结算单存在 | 模板注册表匹配 | 全局待补件 |
| PI-SET-002 | 结算单有客户盖章 | 印章检测 + 主体比对 | 全局待补件/人工复核 |
| PI-CON-001 | 签章促销合同存在 | 合同识别、签章/电子签名核验 | 全局待补件 |
| PI-PAY-001 | 红包/工资打款或批量导出明细存在 | 截图卡片检测或结构化明细读取 | 全局待补件 |
| PI-PAY-002 | 发放主体含本公司名称 | 付款主体字段识别并与公司主数据精确/别名匹配 | 缺失时不得以群名或文件名替代 |
| PI-PAY-003 | 发放状态有效 | 识别“已接收/已收款/成功”等状态 | 失败、撤回或未知记录不计入 |
| PI-PAY-004 | 发放时间在活动期间内 | 逐笔交易日期与活动期间比较 | 顶部手机时间或聊天分隔时间不作为交易日期 |
| PI-PAY-005 | 发放记录唯一且可追踪 | 交易单号优先；组合键和截图配对仅作辅助 | 无交易唯一标识时转人工 |
| PI-PAY-006 | 全部发放明细合计等于核销金额 | 去重后逐笔程序求和 | 不一致时按较低证据金额暂缓差额 |
| PI-DAY-001 | 日结材料（条件规则） | `settlement_mode=daily` 时要求现场照与工资打款凭证 | 条件触发但缺失则待补件 |

人员激励支持金额按证据上限计算：

```text
pos_supported_reward = Σ(min(POS合格数量, 结算数量) × 合同奖励单价)
valid_payment_total  = Σ(去重后、主体有效、状态有效、日期有效的发放金额)

case_supported_amount = min(
  claimed_amount,
  settlement_amount,
  pos_supported_reward,
  valid_payment_total
)
```

盖章 POS、统一结算单、签章合同和有效付款主体均属于全局硬门槛。缺少其中任一项时，不得因为 POS、结算单和截图总金额相同而输出通过建议。

## 4. 总体技术架构

### 4.1 逻辑链路

```text
勤策/钉钉/H5
    → 接入网关与文件归集
    → 材料分类与质量预检
    → OCR/文档理解/现场视觉识别
    → 统一证据模型与证据仓
    → 确定性规则引擎与金额引擎
    → Agent 最终判断与补件说明
    → Decision Guard
    → H5 人工复核
    → 勤策状态回写与审计归档
```

### 4.2 核心组件

| 组件 | 技术职责 | 关键输出 |
|---|---|---|
| API Gateway | 鉴权、限流、幂等、回调验签 | `case_id`、接收回执 |
| Intake Service | ZIP 安全解压、MIME 检测、哈希、病毒扫描、对象存储 | 文件清单、SHA-256 |
| Material Router | 文件分类、场景分类、材料完整性初检 | 材料类型、缺件清单 |
| OCR Service | 文档纠偏、版面分析、文字/表格/印章识别 | 字段级证据 JSON |
| Vision Service | 水印、门店、商品、促销物料、陈列全貌、重复风险识别 | 照片级证据 JSON |
| Spreadsheet Parser | 原生读取 Excel/CSV，保留公式、行号和原始值 | POS/销售明细 JSON |
| Evidence Store | 字段、证据框、页码、行号、哈希、版本关系 | 可追溯证据链 |
| Rule Engine | 硬规则、条件规则、逐项金额计算 | `rule_result[]`、支持金额 |
| Judgment Agent | 汇总机器结论、形成最终建议、生成补件说明 | `audit_decision.json` |
| Decision Guard | 校验状态、金额上限、证据引用和硬门槛 | 可发布审核建议 |
| Review H5 | 原件预览、证据定位、通过/驳回/补件 | 人工审批记录 |
| Integration Adapter | 勤策、钉钉、对象存储及通知适配 | 状态回写、群通知 |

### 4.3 生产化运行方式

- 生产接口以一个核销单为处理单元，不要求地堆和人员激励两个 ZIP 同时提交。
- 每次运行绑定 `source_hashes + ruleset_version + model_version + code_image_digest`，形成不可变运行身份。
- 采用消息队列异步调度，OCR、视觉和规则任务可独立重试；失败任务进入死信队列。
- POC 可使用本地 Agent CLI 和 Git 快照验证；生产环境统一接入模型网关/私有模型服务，不为每单启动 Git Worktree。
- 文件原件只读保存，补件生成新版本，不覆盖历史证据。

## 5. 全流程处理逻辑

### 5.1 状态机

```text
RECEIVED
→ MATERIAL_CHECK
→ EXTRACTING
→ RULE_CHECK
→ AGENT_JUDGING
→ AUTO_PASS / PARTIAL_PASS / NEED_SUPPLEMENT / MANUAL_REVIEW / RECOMMEND_REJECT
→ HUMAN_CONFIRMED
→ SYNCED
```

任何阶段出现不可恢复错误，状态进入 `PROCESSING_FAILED`，保留失败步骤、错误码、重试次数和已完成证据，不将技术失败映射成业务驳回。

### 5.2 分步处理

1. 接收勤策事件或人工上传，按核销单号建立 `case_id`。
2. 校验压缩包安全性、文件魔数、扩展名、大小、页数、图像分辨率和加密状态。
3. 计算 SHA-256，检查本次提交内完全重复，并查询历史指纹库。
4. 识别业务场景和材料类型；低置信度或多义分类转人工选择。
5. 按材料类型执行 OCR、视觉或原生表格解析，输出统一证据 JSON。
6. 规则引擎先检查全局硬门槛，再执行逐 SKU、逐门店、逐笔支付规则。
7. 金额引擎基于规则通过项计算证据支持金额和暂缓金额。
8. Judgment Agent 读取规则结果，生成建议结论、主要风险、补件清单和证据摘要。
9. Decision Guard 验证 Agent 输出；不满足约束时强制降级为 `MANUAL_REVIEW`。
10. H5 展示原件、字段框、规则和计算过程，审核人确认后回写勤策并归档。

## 6. 统一证据数据模型

每个 OCR 或视觉字段必须保留来源，不允许只保存最终文本。

### 6.1 字段证据结构

```json
{
  "evidence_id": "ev_01J...",
  "case_id": "HX-2026-0001",
  "material_type": "settlement_sheet",
  "field_name": "claimed_amount",
  "raw_text": "实际核销金额：7350",
  "normalized_value": 7350.00,
  "source_file_id": "file_01J...",
  "source_sha256": "...",
  "page_no": 1,
  "sheet_name": null,
  "row_no": null,
  "bbox": [0.31, 0.72, 0.58, 0.79],
  "extractor": "settlement-ocr",
  "extractor_version": "1.0.0",
  "confidence": 0.993,
  "validation_status": "validated"
}
```

### 6.2 规则结果结构

```json
{
  "rule_id": "PI-PAY-004",
  "scope_type": "payment",
  "scope_id": "payment_0007",
  "status": "UNKNOWN",
  "severity": "BLOCKER",
  "expected": "交易日期在活动期间 2026-05-01 至 2026-05-20",
  "actual": "截图仅显示星期与聊天时间，未显示完整交易日期",
  "evidence_refs": ["ev_01J..."],
  "amount_impact": 1026.00,
  "supplement_request": "补充包含交易日期、交易单号和付款主体的发放明细"
}
```

### 6.3 数据实体

| 实体 | 主要字段 |
|---|---|
| `audit_case` | case_id、scenario、claimed_amount、activity_period、status、ruleset_version |
| `material_file` | file_id、material_type、object_key、sha256、mime、page_count、version |
| `extracted_field` | field_name、raw_text、normalized_value、bbox、confidence、extractor_version |
| `evidence_item` | 门店/SKU/支付粒度的结构化事实与来源 |
| `rule_result` | rule_id、scope、status、severity、amount_impact、evidence_refs |
| `audit_decision` | 建议结论、支持金额、暂缓金额、阻断规则、Agent 摘要 |
| `review_action` | 审核人、动作、原因、时间、前后状态 |
| `fingerprint_index` | SHA-256、pHash、dHash、图像向量、历史 case_id |
| `model_run` | 模型、提示词版本、输入摘要、Token、耗时、结果状态 |

### 7.2 各 Skill 职责

| Skill | 输入 | 输出 | 自由度 | 失败关闭规则 |
|---|---|---|---|---|

| `extract-audit-documents` | 合同、结算单、盖章 POS | 字段/表格/签章证据 | 中 | 关键字段低置信度输出 UNKNOWN，不补写 |
| `inspect-display-photos` | 原始照片、合同门店 | 逐照片/逐门店视觉证据 | 中 | 文件名不得作为日期或地点独立证明 |
| `inspect-payment-evidence` | 截图、微信导出、工资明细 | 逐笔支付证据与去重候选 | 中 | 无交易唯一标识不得擅自合并同额记录 |
| `audit-promotional-display` | 已验证证据 | 逐门店规则、支持金额 | 低 | 任一强制门店规则 UNKNOWN 时该店金额为 0 |
| `audit-personnel-incentive` | 已验证证据 | 逐 SKU/逐支付规则、支持金额 | 低 | 聚合金额一致不能替代行级匹配 |
| `judge-market-expense-audit` | 规则结果、金额结果 | 最终建议与补件文本 | 中 | 不得修改程序计算金额；违反即降级人工 |

### 7.3 主编排 Skill 工作流

`orchestrate-market-expense-audit/SKILL.md` 固定执行以下步骤：

1. 冻结核销单、源文件和规则版本。
2. 安全校验文件并生成材料清单。
3. 调用材料分类，拒绝模糊路由。
4. 并行调用文档、照片和支付证据 Skill。
5. 对所有模型输出执行 JSON Schema 校验。
6. 调用对应场景 Skill 完成确定性勾稽。
7. 调用判断 Skill 形成审核建议。
8. 调用 Decision Guard 校验最终结果。
9. 生成报告、人工任务和系统回写消息。
10. 保存版本、哈希、规则、证据和人工操作记录。

### 7.4 判断 Skill 核心约束示例

```markdown
---
name: judge-market-expense-audit
description: Generate a constrained final recommendation for a promotional-display or personnel-incentive reimbursement case from schema-validated rule results and deterministic amount calculations. Use only after the scenario audit Skill has completed.
---

# Judge Market Expense Audit

1. Read only validated `rule_result` and deterministic amount outputs.
2. Do not re-extract facts from raw files and do not recalculate money.
3. Apply global blockers before unit-level results.
4. Never convert `UNKNOWN` into `PASS`.
5. Set `suggested_approved_amount` exactly to the supplied guarded amount.
6. Cite at least one rule ID and evidence reference for every blocking reason.
7. If inputs conflict, output `MANUAL_REVIEW`.
8. Return exactly one JSON object conforming to `decision.schema.json`.
```

### 7.5 Skill 验证机制

- 每个 Skill 的 `SKILL.md` 保持短流程，详细规则、字典和 Schema 放入 `references/`。
- 脆弱操作全部封装为 `scripts/`，例如金额重算、Excel 行级读取、哈希、模板注册、规则执行和结果校验。
- 对 Skill 前置/后置条件执行自动测试；缺失引用、Schema 不匹配、规则 ID 不存在均阻断发布。
- Skill、提示词、模型和规则分别版本化，可独立灰度和回滚。
- 新版本先运行历史金标回归，再进入影子模式，不直接影响生产审批。

## 8. OCR 与视觉识别方案

### 8.1 通用图像预处理

所有文档图片先保留原图，再生成识别副本，处理链路如下：

1. 读取并应用 EXIF Orientation，不改写原文件。
2. 通过方向分类器识别 0°/90°/180°/270°，以文本方向一致性二次确认。
3. 检测纸张四边形并做透视矫正；无法稳定检测时保留原图并标记质量风险。
4. 使用霍夫线/文本基线完成小角度去倾斜。
5. 生成原彩、灰度、局部对比度增强、锐化和自适应二值化等多路识别副本。
6. 计算清晰度、曝光、反光、遮挡、裁切和最低有效分辨率。
7. OCR 同时执行全页识别和模板 ROI 识别；关键字段需多路结果一致或进入复核。

样例结算单存在 90° 旋转、拍摄透视、页面弯曲及红章覆盖日期等情况，因此不得只做一次全图 OCR。印章区域需在彩色图上单独检测，同时在“保留红章”和“弱化红章”两种副本上识别被覆盖文字，并将冲突字段标记为人工确认。

### 8.2 材料分类

材料分类使用“规则优先、模型补充”的组合：

- 文件魔数与原生结构：识别 PDF、Excel、CSV、图片和压缩包。
- 文件名关键词仅作为弱特征，不直接决定材料类型。
- 文档首页缩略图 + OCR 标题 + 版面特征判断合同、结算单、盖章 POS、发放明细。
- 图片 UI 结构判断红包/转账截图，场景视觉特征判断地堆/陈列照片。
- 分类置信度不足或一个文件命中多个材料类型时，输出 `classification_ambiguous`，由人工选择。

### 8.3 统一结算单 OCR

1. 建立结算单模板注册表：`template_id`、版本、参考图、Logo/标题/表头锚点、关键 ROI 和允许版式偏移。
2. 使用特征点与单应性矩阵将拍照件对齐至参考模板。
3. 同时抽取客户名称、项目类型、活动期间、SKU/门店明细、数量、奖励单价、行金额、合计、实际核销金额、签署日期和客户盖章。
4. 表格采用“版面检测 → 行列结构 → 单元格 OCR → 行列求和校验”，不以一段自然语言替代表格。
5. 模板一致性由锚点覆盖率、表头顺序和布局相似度共同判断；仅标题相同不足以认定统一模板。
6. 结算行合计、表内总计和实际核销金额分别保存，差额由规则引擎计算。

### 8.4 合同 OCR 与签章

- 对文本 PDF 优先读取文本层，同时渲染页面进行版面和签章检查。
- 对扫描 PDF 执行逐页 OCR，提取合同主体、项目类型、活动起止日期、门店清单、执行标准、奖励/单店费用、预算/合同金额、付款条件和附件页。
- 对签章检测输出 `seal_visible`、`signature_visible`、印章文本、印章主体匹配状态和证据框。
- 若 PDF 含数字签名，校验证书链、签名覆盖范围、签名时间和文档修改状态；没有数字签名时明确输出“未提供”，不得用 SHA-256 代替。
- 合同门店清单必须保留原始序号和页码，作为照片绑定主键。

### 8.5 盖章 POS 与电子 POS

- 电子 POS 使用原生 Excel/CSV 解析，保留工作表、Excel 行号、公式和原始单元格值。
- 表头通过可配置同义词识别；条码字段强制按字符串读取，避免科学计数法和前导零丢失。
- 过滤空行、分组合计和总计行，但保留被过滤行及原因。
- 逐行标准字段包括日期、经销商、门店、SKU/条码、商品名称、数量、单价和金额。
- 盖章 POS 图片/PDF 通过 OCR 结构化后，与电子表按文件总计、门店合计及 SKU 合计三层勾稽。
- 盖章 POS 只有总计、无明细时，记录其证明范围，不将总计一致替代电子表逐行校验。

### 8.6 红包、转账及工资打款识别

样例截图同时展示“已被接收”和“已收款”的左右两侧消息，同一金额可能是同一笔交易的双方视图，也可能是不同交易。系统按以下逻辑处理：

1. 使用 UI 组件检测模型切分每个支付卡片，识别左右方向、金额、状态、头像/会话对象、可见时间和卡片位置。
2. 顶部手机时间仅作为截图时间；聊天分隔时间只作为会话时间。二者均不得直接写入交易日期。
3. 交易详情页或批量导出中的交易单号是首选唯一键。
4. 只有业务证据明确表明左右卡片为同一交易时才合并；同额记录默认分别保留。
5. 截图组合键可使用 `交易单号 + 金额 + 收款人 + 完整交易时间 + 付款主体`。字段不全时只生成“疑似配对”，不自动去重。
6. 群名、联系人名称或文件名不能代替付款主体中的“本公司名称”。
7. 优先接入微信批量导出或发放系统导出明细；截图作为辅助证据。结构化明细必须校验字段完整性、总笔数、唯一交易号和总金额。
8. 计算有效支付总额前，逐笔排除失败、撤回、未知状态、期外和付款主体不匹配记录。

### 8.7 地堆照片水印 OCR

- 使用全图 OCR 与水印检测器并行，不固定只截取图片底部，以适配不同水印相机版式。
- 对候选水印区生成局部对比度增强、白字边缘增强、反色和多尺度副本。
- 通过日期、时间、行政区、地址关键词及水印相机标识做字段切分。
- 日期统一转为 ISO 格式；只有月日时必须结合合同年份且标记“年份推定”，不得自动通过关键日期规则。
- 地址经行政区划规范化、地理编码和门店主数据匹配，输出精确、已确认兼容、冲突或不可验证。
- 同时读取 EXIF 时间和 GPS；与画面水印冲突时按高风险转人工，而不是选择其中一个。

### 8.8 地堆/陈列视觉识别

每张照片输出独立子任务：

- `scene_complete`：是否包含堆头/货架完整边界，是否严重裁切、遮挡或模糊。
- `target_product_present`：是否可见活动商品/品牌，输出证据框。
- `promotion_sign_present`：是否可见价签、促销牌或活动物料。
- `display_type`：堆头、端架、普通货架、其他。
- `facing_count`：可稳定识别时输出纵列数及置信度。
- `area_verifiability`：是否具备面积尺度参照；无参照时为 `unverifiable`。
- `store_scene_consistency`：门头、店内标识和水印地点是否互相一致。

视觉模型只输出观察事实和证据框。是否满足合同标准由规则引擎根据合同结构化条款判断。

### 8.9 重复与复用检测

采用四层指纹：

1. SHA-256：发现字节级完全相同文件。
2. dHash/pHash：发现缩放、压缩后的视觉近似候选。
3. 局部特征/图像向量：发现裁剪、加水印、轻度调色后的复用候选。
4. 历史指纹库：跨活动、跨经销商、跨门店查询复用。

阈值必须在客户历史样本上标定。精确哈希重复可直接阻断对应证据；近似候选只生成风险任务，由复核页并排展示，不因单一相似度自动判定舞弊。

## 9. OCR/视觉模型微调方案

### 9.1 分阶段策略

| 阶段 | 技术策略 | 适用条件 |
|---|---|---|
| A：规则与模板校准 | 通用 OCR + 图像预处理 + 模板 ROI + 字典/正则 + 多路一致性 | 样本较少的 POC/首版 |
| B：识别模型微调 | 使用真实错例和合成样本微调文字检测/识别 | 已积累稳定标注的难例 |
| C：专用检测模型 | 微调印章、水印、支付卡片、陈列要素检测 | 业务版式稳定且样本量足够 |
| D：持续学习 | 人工改判回流、主动学习、漂移监控、灰度发布 | 生产稳定运行后 |

首版不建议直接对大模型进行全参数微调。优先通过模板注册、证据 Schema、字段词典、规则和小模型检测解决确定性问题；只有稳定重复出现的 OCR 错误再进入识别模型微调。

### 9.2 标注规范

- 文档类：文档类型、页方向、页面四角、字段框、字段文本、表格行列、印章框、签字框、模板版本。
- 支付类：每个卡片框、消息方向、金额、状态、付款/收款主体、收款人、交易日期、交易单号、截图间配对关系。
- 水印类：水印整体框、日期框、时间框、地址框、行政区及水印来源。
- 陈列类：堆头/端架/货架框、活动商品框、促销标识框、纵列、全景/局部、遮挡、模糊和不合格原因。
- 所有标签区分“未出现”“出现但不可读”“模型无法确定”，不得统一标为空字符串。

### 9.3 数据集建议

- 初始回归集应覆盖各材料类型、拍摄方向、清晰度、不同手机/水印相机、不同客户印章和不同模板版本。
- OCR 识别微调建议累计不少于 3,000 条高质量难例文本行；金额、日期、公司名和地址需单独分层抽样。
- 印章/水印/支付卡片检测建议每类至少数百张正样本，并配置 1～2 倍困难负样本。
- 陈列视觉任务建议从 1,000 张以上逐项标注照片起步；若样本不足，先使用通用视觉模型并全部经过规则与置信度门控。
- 训练、验证、测试按客户/活动/时间/设备分组切分，近似图片不得跨集合，避免数据泄漏。
- 真实业务样本不足时可做旋转、透视、压缩、模糊、反光、阴影、印章覆盖和字体扰动等合成增强，但测试集必须全部为未增强真实样本。

### 9.4 词典与归一化

- 公司主体库：本公司法定名称、曾用名和经审核别名。
- 经销商库：标准名称、统一社会信用代码、印章文本和允许别名。
- 门店库：门店编码、标准名、简称、历史更名、地址、经纬度及有效期。
- 商品库：条码、标准商品名、规格、活动别名和有效期。
- 日期解析：中文年月日、点号/横线/斜线、月日区间、聊天相对日期。
- 金额解析：人民币符号、千分位、小数、中文大写金额；所有金额使用 Decimal，禁止浮点财务计算。

别名必须由业务人员确认后进入版本化主数据，模型不能自行把相似门店名写入正式映射。

### 9.5 置信度校准

原始 OCR 分数不能直接作为业务通过阈值。需在 UAT 金标集上做字段级校准，并按关键程度分层：

- 金额、日期、交易单号、条码、客户主体等关键字段：要求高阈值且多路识别一致。
- 门店/地址：要求高置信度，并通过主数据或人工确认别名。
- 描述类文本：允许较低阈值，但不直接驱动金额。
- 任一关键字段的多路结果冲突，状态为 `UNKNOWN`。

初始可配置 `critical ≥ 0.98`、`identity ≥ 0.95`、`descriptive ≥ 0.90` 作为工程起点，最终阈值以客户金标集达到目标误报率为准，不直接使用供应商未校准的置信度。

### 9.6 持续优化闭环

1. 人工复核页记录原识别值、改正值、改正原因和最终结论。
2. 每周自动聚类低置信度、模型冲突、频繁补件和人工改判样本。
3. 选择高价值难例进入标注队列，形成增量训练集。
4. 新模型执行离线金标回归、影子运行和小流量灰度。
5. 只有关键指标不下降且无新增高风险漏判时才全量发布。
6. 保留旧版本及阈值，一键回滚；历史结果不被新模型静默改写。

## 10. 确定性规则与金额引擎

### 10.1 执行顺序

1. 文件安全与可读性。
2. 场景和材料完整性。
3. 全局主体、模板、签章和合同门槛。
4. 活动期间。
5. 地堆逐门店或人员激励逐 SKU/逐门店。
6. 支付明细去重与有效性。
7. 金额上限计算。
8. 风险合并和建议状态映射。

### 10.2 规则配置

规则采用版本化 YAML/JSON 配置，示例：

```yaml
rule_id: PI-PAY-002
scenario: personnel_incentive
scope: payment
mandatory: true
condition: payment.channel in [wechat_redpacket, salary_transfer]
assertion: payment.payer_company_id == case.company_id
on_unknown: NEED_SUPPLEMENT
on_fail: MANUAL_REVIEW
amount_effect: exclude_payment
```

规则变更必须经过业务/财务确认、配置审核、回归测试和版本发布。历史核销单继续绑定原规则版本。

### 10.3 金额安全约束

- `suggested_approved_amount ≤ claimed_amount`。
- 地堆建议金额不得超过全局材料有效情况下的合格门店费用之和。
- 人员激励建议金额不得超过结算金额、POS 支持奖励和有效付款金额中的最小值。
- `UNKNOWN` 对应金额不计入自动支持金额。
- Decimal 精确到分；舍入方式由规则配置，不允许 Agent 自行解释尾差。
- 所有聚合必须能够下钻到 Excel 行、合同门店或交易明细。

## 11. Agent 最终判断设计

### 11.1 Agent 的输入与职责

判断 Agent 不直接读取原始图片重新识别，只接收：

- 材料完整性结果；
- 字段级验证状态；
- 逐门店/逐 SKU/逐支付规则结果；
- 确定性支持金额、暂缓金额和差额；
- 风险等级、证据引用和补件模板；
- 当前规则版本和业务场景。

Agent 负责把机器结果组织为客户和审核人员可理解的最终建议，合并重复异常，给出优先级明确的补件清单，并说明建议金额的构成。Agent 不得生成规则中不存在的例外，也不得基于“看起来合理”覆盖阻断项。

### 11.2 建议状态

| 状态 | 技术定义 | 金额处理 |
|---|---|---|
| `AUTO_PASS` | 所有全局和明细硬规则 PASS，关键字段高置信，无未解决异常 | 建议全额通过 |
| `PARTIAL_PASS` | 全局材料完整，部分可分割门店/SKU 通过，部分失败或待补 | 仅建议证据支持部分 |
| `NEED_SUPPLEMENT` | 必交材料缺失、关键字段不可读或证据不足 | 全局缺件时建议金额为 0 |
| `MANUAL_REVIEW` | 证据冲突、别名未确认、近似重复、支付身份/日期不确定 | 不自动放行，由人工决定 |
| `RECOMMEND_REJECT` | 确认期外、主体冲突、重复核销、金额明显虚报等硬性事实 | 建议驳回对应部分或整单 |

### 11.3 Decision Guard

Agent 输出后必须执行以下校验：

- JSON Schema 完整且枚举值合法。
- 建议金额等于规则引擎提供的 guarded amount。
- 存在全局 blocker 时不得输出 `AUTO_PASS` 或非零自动建议金额。
- `UNKNOWN` 不得在摘要中描述为已通过。
- 每个 blocker 必须引用存在的规则 ID 和证据 ID。
- Agent 不得新增或删除明细级金额。
- 结论与规则状态不一致时强制改为 `MANUAL_REVIEW`，记录 `AGENT_GUARD_REJECTED`。

## 12. 接口与集成设计

### 12.1 核心 API

| 接口 | 方法 | 用途 |
|---|---|---|
| `/v1/audit-cases` | POST | 创建核销单并返回 `case_id` |
| `/v1/audit-cases/{id}/materials` | POST | 登记或直传材料 |
| `/v1/audit-cases/{id}/submit` | POST | 冻结当前版本并启动审核 |
| `/v1/audit-cases/{id}` | GET | 查询状态与进度 |
| `/v1/audit-cases/{id}/result` | GET | 获取审核建议、规则和证据 |
| `/v1/audit-cases/{id}/supplements` | POST | 提交补件并生成材料新版本 |
| `/v1/audit-cases/{id}/review` | POST | 人工通过、驳回或要求补件 |
| `/v1/callbacks/qince` | POST | 回写勤策结果与同步状态 |

### 12.2 幂等与回调

- 创建请求使用 `external_case_id + request_id` 保证幂等。
- 文件以 SHA-256 去重；同一文件重复上传只新增关联，不重复存储。
- 回调使用时间戳、随机数和签名验签，支持指数退避重试。
- 勤策字段映射至少包括核销单号、场景、AI 建议状态、建议金额、暂缓金额、主要异常、复核人、复核时间和同步状态。
- 钉钉群消息只展示摘要和安全链接，不直接暴露敏感明细。

## 13. 人工复核 H5

复核页按“结论 → 阻断项 → 金额 → 原始证据”的顺序展示：

- 顶部显示建议状态、申报金额、证据支持金额、建议金额和暂缓金额。
- 全局缺件单独置顶，不与低风险提示混合。
- 地堆按合同门店逐行展示照片、水印、地点、日期、陈列结论和金额影响。
- 人员激励按 SKU、门店和支付三种视图下钻。
- 点击字段可定位到 PDF 页、图片证据框或 Excel 行。
- 重复候选支持并排原图、缩放和指纹距离展示。
- 审核人可通过、部分通过、驳回或要求补件，必须填写原因。
- 人工修改关键字段时保存修改前后值、来源、人员和时间；修改后重新运行受影响规则。

## 14. 安全、审计与隐私

- 文件存储和数据库启用静态加密，接口全程 TLS。
- 使用最小权限服务账号和 RBAC；经销商、业务、财务和管理员权限隔离。
- 原始文件采用只读对象和版本化存储，下载使用短期签名 URL。
- 日志不记录完整图片、身份证号、手机号、Cookie、Token 或模型密钥。
- 外部模型调用经过模型网关，配置数据不用于供应商训练、区域和留存策略；高敏场景可全部私有化部署。
- 保存源文件哈希、模型版本、提示词版本、规则版本、代码镜像摘要、调用耗时和结构化结果。
- 数据保留期限、归档和删除由客户制度配置；删除操作保留审计事件但不保留敏感正文。
- 历史指纹库只存必要指纹和 case 引用，访问受审计权限控制。

## 15. 稳定性与运维

- OCR、视觉、规则、报告和回写拆分为可重试任务，使用幂等任务 ID。
- 同一页连续两次模型失败后切换备用识别路径；达到最大次数进入人工，不无限重试。
- 监控任务积压、P95 耗时、OCR 失败率、字段 UNKNOWN 率、人工改判率、模型用量和回写失败率。
- 设置模型熔断和预算上限，异常时降级为本地 OCR + 人工复核，不丢失源文件。
- 生产规则、模型和提示词支持灰度、影子运行及快速回滚。
- 建议性能目标：20～30 张照片、合同/结算单和 1 份 Excel 的标准核销包，P95 在 5 分钟内完成机器初审；最终指标按部署资源压测冻结。

## 16. 测试与验收

### 16.1 必测用例

- 结算单旋转 90°、透视变形、红章遮挡日期、表格行缺失。
- 统一模板正确、旧版模板、非统一模板和伪相似模板。
- 合同缺页、未签章、扫描章、电子签章和签后修改。
- 地堆照片无水印、日期期外、地点冲突、只有文件名、画面局部、商品缺失、促销标识缺失。
- 相同照片改名、压缩、裁剪、加水印及跨活动复用。
- POS 条码科学计数法、前导零、合计行、公式、外部链接和多工作表。
- 盖章 POS 与电子 POS 总计一致但 SKU 明细不同。
- 红包截图左右镜像、相同金额多笔、只有手机顶部时间、缺公司名称、缺交易单号、期外发放。
- POS、结算单、合同和付款四方金额分别不一致。
- OCR/模型超时、Schema 不合法、规则服务失败、勤策回写失败。

### 16.2 建议验收指标

最终阈值以客户确认的独立金标集为准，建议目标如下：

| 指标 | 建议目标 |
|---|---|
| 必交材料缺失检出率 | 100% |
| 关键金额/日期/交易号字段精确匹配率 | ≥ 99% |
| 客户、门店和商品标准化准确率 | ≥ 97% |
| 表格有效行召回率 | ≥ 98% |
| 确定性金额计算错误 | 0 |
| 自动通过精确率 | ≥ 99.5% |
| 高风险异常召回率 | ≥ 98% |
| 证据引用覆盖率 | 100% |
| 技术失败被误判为业务通过/驳回 | 0 |

自动通过精确率优先于覆盖率。系统首期可将较多案件送人工，待数据积累和阈值稳定后再逐步提升自动化率。

### 16.3 回归与发布门禁

- 所有金额公式、规则状态映射和 JSON Schema 单元测试通过。
- 历史金标集关键指标不得下降。
- 新增模型在影子模式下与人工结论对比，达到门槛后小流量灰度。
- 高风险漏判为发布阻断问题；低风险召回提升不得以降低自动通过精确率为代价。
- 输出 Excel/JSON 的合计、公式、证据链接和文件哈希必须通过自动校验。

## 17. 实施与上线计划

### 阶段 1：规则与数据契约冻结

- 确认两类业务的必交材料、条件材料、全局 blocker、可分割金额规则和人工权限。
- 获取统一结算单模板、公司/经销商/门店/商品主数据及允许别名。
- 冻结 evidence、rule result 和 audit decision Schema。

### 阶段 2：OCR/视觉与规则引擎建设

- 完成结算单、合同、盖章 POS、支付明细和现场照片识别。
- 完成逐门店、逐 SKU、逐笔支付的确定性程序。
- 建立指纹库、模板注册表、模型注册表和规则版本库。

### 阶段 3：Agent 判断、H5 与系统集成

- 上线判断 Skill 与 Decision Guard。
- 完成 H5 证据定位、人工操作、钉钉通知和勤策回写。
- 建立完整审计日志、监控、重试和异常降级。

### 阶段 4：历史回放与 UAT

- 使用脱敏历史案件建立金标集，覆盖通过、补件、部分通过和高风险样本。
- 执行离线回放、误差分析、阈值校准和一轮客户 UAT。
- 冻结验收阈值、规则版本和生产发布清单。

### 阶段 5：影子运行与灰度

- 首期 Agent 只给建议，不自动回写最终审批。
- 对高置信案件逐步开放自动建议通过；所有异常和低置信案件继续人工确认。
- 根据人工改判持续优化模板、字典、规则和模型。

## 18. 现有验证工程的生产化改造重点

现有样例工程已经具备安全解压、场景路由、Excel 原生读取、图片哈希、逐 SKU/逐门店勾稽、结果 Schema 校验和 Excel 报告等基础能力。生产化需重点完成以下升级：

1. 从“两个 ZIP 固定成对运行”改为“单核销单独立异步运行”。
2. 从“Agent 一次性读取附件”改为“专业 OCR/视觉服务输出字段级证据”。
3. 将地堆统一结算单和客户盖章纳入全局硬门槛。
4. 将人员激励盖章 POS、签章合同、本公司名称、完整发放时间及交易唯一性纳入全局硬门槛。
5. 补充统一模板版本识别、印章主体 OCR、电子签名校验和批量发放明细解析。
6. 将截图同额配对由模型推断改为“交易单号优先、证据不足不合并”。
7. 从本案内哈希去重升级为跨活动历史指纹检索。
8. 增加字段 bbox、页码/行号、识别置信度、模型/提示词/规则版本等证据元数据。
9. 增加 Judgment Agent 与 Decision Guard，确保 Agent 建议不突破确定性金额和硬规则。
10. 用不可变容器镜像和版本化配置替代生产每单 Git Worktree，同时保留同等可追溯性。

## 20. 最终技术结论

本项目的可靠落地路径不是让单一大模型直接“看附件后判断是否通过”，而是构建一条可验证的证据流水线：

```text
专业识别得到事实
→ Schema 固化事实
→ 程序执行硬规则和金额计算
→ Agent 形成最终建议与补件说明
→ Guard 校验 Agent
→ 人工确认并留痕
```

在该架构下，地堆核销可以下钻到每家合同门店和每张现场照片，人员激励可以下钻到每个 SKU、每家门店和每笔发放记录；缺少统一结算单、客户盖章、签章合同、盖章 POS、付款主体或完整发放时间等关键证据时，系统不会因金额相同而误判通过。最终方案同时满足自动化效率、财务金额安全、客户审核口径一致和全链路可追溯四项要求。
