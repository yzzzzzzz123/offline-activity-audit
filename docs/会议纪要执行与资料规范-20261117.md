## 现有Agent分工与模型

沿用一个主Agent及三个子Agent，不新增照片Agent：

- 照片Agent `visual`：千问3.8 Max，负责照片、水印、商品外观、陈列/尺寸、通用造假疑点和本角色自检。
- 文档Agent `documents`：DeepSeek，负责资料盘点、合同、结算、印章、主体和期间逻辑。
- 金额Agent `numbers`：DeepSeek，负责原生POS、商品编码身份及金额计算逻辑。
- 主Agent `main`：DeepSeek，接收三个子Agent的结构化结果，完成冲突复核调度和汇总。

所有原图读取及定向回看都归照片Agent并使用千问，包括PDF扫描页和商品参考图。每次仍最多一张原图；原图独立读取，不回放此前错误转录。文档或金额Agent需要看图时，先委托照片Agent独立读取像素，再将来源绑定事实交回其DeepSeek会话完成文字或金额逻辑。所有照片内容判断与照片自测也只归照片Agent；其他角色不能另作照片结论。外采赠品的执行证明汇总须等待并引用照片Agent的有效性/覆盖结果，POS部分仍依据实际POS资料核对。商场入场协议属于文档责任。

每单启动时冻结两套连接。照片密钥与DeepSeek密钥分别存储，Windows使用当前用户DPAPI保护；不写入源码、文档、日志或公开API。修改照片配置只影响后续启动任务，不改在跑任务与历史结果。原图事实缓存使用实际图片模型、端点、推理强度、凭据范围和读取契约，不能把DeepSeek旧事实当成千问新识别。

界面按用户最后确认保留记录内的真实模型和用量：删除“更换模型”模块，顶部不展示“当前模型＋分工”。“审核工具”显示本单主模型及实际参与的图片模型；DeepSeek、Qwen用量各分两行，第一行模型和合计，第二行输入/输出，左侧分别为蓝色、绿色细竖线，无框、无底色。总用量仍为输入加输出，缓存命中和推理Token属于子集，不重复相加；失败重试按真实返回分别累计，同次调用只计一次。尚未返回时显示等待，历史缺失模型归属单独标记，不根据当前配置猜测。

总览“平均 Token 消耗”卡片保持原来的106px高度，默认只显示总平均值，单击在同一卡片内切换到DeepSeek/Qwen明细，再单击返回；Enter或空格键也可切换。明细沿用彩色竖线区分，展示各模型平均用量及输入/输出，不增高卡片或弹窗。平均用量保留原有去掉一个最高值、一个最低值的规则；每个模型独立使用完整用量样本，输入/输出与合计采用相同的保留样本，显示参与样本数，不把未调用或未记录当零。统计读取已有日志，不重审或改写历史结果。

## 资料提交和拍摄建议

1. 按核销类型准备一份完整ZIP，保留原文件，合同和需要验章的文件以PDF提交，同时保留要求的原生Excel。
2. 先拍能辨认门店与陈列范围的正面全景，再补商品包装、价签、水印及必要侧面近景；同一门店的照片应能相互对应。
3. 主货架、端架和地堆分别保留完整陈列范围。倾倒、倒置、过度遮挡和杂乱堆放会降低识别效果；拍摄建议本身不新增拒付条件。
4. 保留原始水印，不拼接、覆盖或修改日期、地址。已确认的“水印时间位置读到数字即认可拍摄时间存在”规则保留，不补造完整时分秒。
5. 新品、改码或包装更新时维护实际商品编码、规格、当前包装参考图及尺寸。未维护资料由业务和商品资料维护人员处理，不让AI猜测。
6. 印章应单独、清晰、完整，避免重叠；不通过复制另一文件的印章形成所谓盖章文件。

## 回归与验收清单

| 样本 | 应观察的行为 |
| --- | --- |
| CVS/OTC仅交完整POS | 不再同时追库存；仍核对门店、商品及照片覆盖 |
| 外采仅POS / 仅合格照片 / 两者都无 | 前两者分别走对应分支，最后一种合并提示执行证明缺口；三者采购票据要求一致 |
| 不同章种及重叠章 | 按文件类型区分，无法辨认列人工复核，不能假称无章或合格 |
| 扫描PDF、真正图片、伪装PDF扩展名 | 以真实原文件格式及资料角色判断，不能把所有图片拒绝或把渲染PNG当原文件 |
| POS只有金额，没有数量汇总或单价 | POS达标激励不因此报缺件；其他类型保持原要求 |
| 结算POS金额等于、低于、高于完整实际POS金额 | 等于、低于可满足支撑；超过则具体说明不足，字段和期间必须一致 |
| 10店×10条码，删掉2个商品的现场证据 | 照片Agent逐店逐商品指出缺口；其他门店同码不能补齐。需要实际图像验收，规则文本和差集算法不代表识别率已达标 |
| 改水印、复用底图、年份与星期矛盾 | 定向查看涉及原图并引用具体证据；不能用相似指纹直接判造假 |
| 单附件不可读、接口超时、数据库故障 | 已读来源保留；内部故障与客户缺件分开，不把未完成当通过 |
