# 2026-09-14 AI 长时间运行排查与修复

时间均为北京时间。问题入口为 `http://192.0.0.148:8080/`。

## 原因与证据

主因是模型网络不通。工作台模型子进程使用的本机代理 `127.0.0.1:7897` 当时处于 `direct` 模式；代理服务日志显示 `codex.exe → chatgpt.com:443 → DIRECT`，连接持续超时。经该端口访问 OpenAI 出现 TLS 握手失败，而普通网站可访问。独立、不带业务材料的模型探针也收到断流、握手和重连事件，未观察到模型输出。因此，当时的“运行中”不能解释为模型一直在分析。

旧调用器使用阻塞式 `subprocess.run`，直到进程退出才处理输出。单次 1200 秒、最多三次重试，加上超时后没有保留安全进度，使一个纯网络故障可占用队列约一小时。最初任务约 15:13 开始，16:13 结束三次失败尝试。该记录和对应材料后来已被删除，本次修复没有恢复它。

20 分钟原本是**单次模型调用**限制，不是整个核销任务的限制。此前可读取的成功记录中，单次调用最长约 4.7 分钟，但一个包含 72 次调用的完整任务耗时约 59 分钟。长任务和连接故障需要分别判断。

## 已实施修复

- 为 AI 建立独立、仅监听本机的代理 `http://127.0.0.1:7898`，复用用户已有可用节点；原有全局代理仍为 `direct`。只设置 `OFFLINE_AUDIT_MODEL_PROXY`，OSS 下载和回调继续使用原有路径。
- 专用代理启动器位于 `%LOCALAPPDATA%\OfflineActivityAudit\model-proxy\launch.py`，设置文件只引用既有配置，不复制凭证。配置运行时临时生成，内核加载后删除；已登记当前用户登录启动项 `OfflineAuditModelProxy`。
- 在不重启工作台、不丢弃排队任务的情况下更新现有服务的模型代理环境。对已确认归属的失败模型子进程结束当前尝试，保留核销 runner，由原有重试流程继续执行。
- 新调用器持续读取 stdout/stderr，每 30 秒输出受控阶段、耗时、模型事件及连接异常计数；本地启动和重连不算模型输出，不持久化原始推理和诊断正文。
- 单次总时限默认延长到 3600 秒。明确模型连接错误连续 120 秒没有恢复时结束当前尝试；正常分析与网络故障分别计时。两项均可显式配置。独立遥测失败不触发提前终止。
- Windows 模型进程放入本次调用专属 Job Object，退出时清理全部后代，避免后代占用管道造成假运行。
- 维护费用的 POS 视觉材料、合同、结算单分别读取，其他同角色材料每批最多三份；同一 PDF 保持完整。仅重试失败批次，已完成批次保存已校验证据；最后校验整包来源、角色、数量和顺序。
- 模型仍为 `gpt-6-astra`，推理仍为 `medium`。
