# 客户结果写法

2026-09-22最新要求：所有面向人的文字都要简单、易懂，包括对话、进度说明、页面、报告摘要和回调。每条直接说具体问题，不在前面加“压缩包名.zip：人员激励：”“缺少资料：”“尚不能确认的资料或适用情况：”等套话。核销类型放在分类标题，压缩包名放在记录标题；多包时只在各包分组标题写一次，不能合并不同包的问题。

例如直接写“缺少盖章版销售明细。”“缺少促销合同。”“无法确认是否安排临促、是否需要临促照片。”不加“（POS）”等无助于理解的术语。已经具体指出缺少哪一版销售明细时，不再另列“两版须成套提供”的重复提醒。

写一至两句能理解的话，先说问题，必要时补原因。只在定位问题确有必要时写原始业务文件名、门店、日期、商品、双方数值和差额；不要把全部附件名堆在句首。不删掉不同对象、实质差异或不能确认的原因，不把“看不清”“还不知道是否需要”改成“没交”。内部规则编号、审核过程及推理约束留在技术记录。

用户2026-09-21最终确认：bizType为必填字符串，只允许条码费、陈列堆头、人员激励、POS达标激励、搭赠、KT板等物料制作、补差、外采赠品这八个规范值进入AI核销。程序按原值精确匹配、一一对应八个Skill，不调用AI选型，不接受旧称、同义词、内部标识、大小写变体或模糊匹配。命中后AI只核对指定Skill资料门禁；资料内容、ZIP名和文件名不能改变类型。缺少、多余及条件不明逐项列问题并正常完成，不判核销失败；门禁满足后才业务审核。其他非空bizType正常完成，不下载资料、不调用AI，回调result精确为“该业务类型无需AI核销”。缺失、null、空字符串或纯空白仍失败，回调result精确为“无法识别核销类型”。非字符串返回400。未携带bizType的历史直接input兼容入口保留内容分类，新OSS任务不能回退。

本规则来自用户2026-09-21要求，适用于八类核销Skill、客户回调中的AI小结和后台可见页面。阅读者不熟悉财务和系统术语，可能只想知道哪份资料要处理。原始数值、模型记录和程序日志仍保存在技术档案，不能用简单说法改掉事实或判断标准。所有业务问题必须有本类型“审核要点/标准”栏出处；资料说明和背景不是客户错误依据。

业务背景只供理解流程，有则参考，没有不影响核销。缺少背景资料、BI额度管理、申请先后、提交受理时限、财务一审及补交期限、额度返还、罚款及人事处理，不列入客户小结、回调或后台问题列表；不从这些流程信息推导额外核销条件，实际核销规则仍照常检查。区分方法见 [业务背景](business-background.md)。

## 每个问题怎么写

用一至两句日常中文先说问题；需要时再说原因或要求。有门店、商品、日期、页码或表格位置时，只保留帮助客户找到问题的信息。文件显示原文件名，不显示电脑路径、临时文件名或内部编号。

- 没交：盘点全部资料后，才能说“没有收到……”。不能只因为文件名没写，就说没交。
- 交了但缺内容：说“《……》没有写……”。不要把整份文件说成没交。
- 看不清：说“《……》第……页的……看不清，暂时不能确认……”。不能说一定没盖章、填错、过期或造假。
- 两份不同：写清两份原文件、同一门店/商品/日期和不一致的内容。数字比较给出双方原值，必要时说明相差多少，不能只说“存在差异”。不要把销售单价和奖励单价当作一回事。
- 缺比较依据：说“目前资料里没有……，暂时不能判断……”。这不等于要求客户新增一类必交文件；只说明判断缺少的信息，不擅自要求截图、证明、印章或新表格。
- 规则还没确认：说明具体哪个标准没有确定，不能当成客户填错。其他可以检查的项目继续检查。

客户原因只写这一项实际问题，不照抄整条规则，不把所有可能缺件列一遍，不夹“建议补充完整资料”“需人工核验”等空话。必要的补正动作只指向已明确要求的具体内容，不能增加条件。审核栏写“直接0核销”等后果时，AI也只输出具体错误点，由人工复核决定；不写不能报销、不予核销或整单/部分核销结论，不宣称已扣款、罚款或发了通知。

## 用词

优先用“销售明细”“商品”“商品条码”“两份内容是否一样”“照片是否清楚”“还不能确认”。客户原因不用“核验闭环”“口径不一致”“证据链”“唯一匹配”“字段完整性”“归因”“置信度”“unknown”“rule_id”等词。门店原名、商品原名、品牌名称、文件名、条码和真实数值必须保留，不得为简化措辞而改名。

已确认通过的项目可以说“已核对，两份……相同”。“暂时不能确认”始终作为待处理问题显示，不能混进已通过项目。界面和回调引用同一组问题，不再另让模型改写一遍造成意思变化；原始记录只在技术档案中展示。

按用户2026-09-22确认，已有金额支持检查允许凭证金额多于本次核销金额，不能因为两边不相等就列问题。用户同日确认申报单价少于或等于合同约定也通过；单价超出时明确说申报单价比合同约定多了多少，不把单价差异写成核销总额超支。通过时可说“本次凭证金额足够支持本次核销金额”，不要把不相等的原值写成相同。金额不足时写清本次核销金额、凭证合计及少了多少；POS金额复算不足也写清列示金额、复算金额和差额，不用四舍五入或一分钱容差抵消不足。

核销类型未确定时，按实际清单分别说明缺少、多余或不能确认的资料及相关文件，不按最接近的类型猜测缺件；正常完成资料检查，不报核销失败。系统处理失败与资料不合格分开：系统错误可说“这次处理没有完成，请联系工作人员查看”，不显示程序异常、服务器路径或接口信息，不让客户凭系统故障重交业务资料。

## 例子（均为假设，不是固定业务数值）

| 情况 | 客户看到的话 |
| --- | --- |
| 陈列照片没写日期 | 《陈列照片.jpg》有地址，但没有拍摄日期，无法确认是否在活动期间拍摄。 |
| 某店临促少一天照片 | 合同安排甲店9月1日至3日做临促，甲店目前只有1日和3日的照片，缺2日照片；乙店2日的照片不能代替甲店。 |
| 临促照片缺少画面内容 | 《甲店9月2日.jpg》有水印和产品，但没有看到临促人员。 |
| 大额红包缺公司名 | 红包截图是1200元，但没有写经销商公司名称。超过1000元的红包需要写经销商公司名称。 |
| 本次红包合计不足 | 《结算单.xlsx》本次核销100元，《红包截图.jpg》本次红包合计99.99元，少了0.01元。 |
| 参照资料不明 | 目前资料里没有这次活动批准的奖励单价，暂时不能判断结算单上的单价是否正确。 |

例子只示范写法；实际输出必须使用本次资料中的名称、日期、数值和已有判断，不能照搬例子内容。

条码费地址重复只报告不同申报门店使用同一地址的情况，写清两个申报门店、实际地址及来源。已确认同店的多张照片即使地址相同也不列问题；归属不明写清哪张照片不能对应哪家门店，不认定跨店重复、重复核销或造假。

## 商品库缺少对应商品（2026-09-22用户确认）

针对对应商品直接写“库内无参考商品”，保留商品名称或编码，不改成客户未交照片、商品未上架或商品不合格，不追加处理建议。示例：“小箭头蓬松控油洗发水500ml（CP-XH-XFS-0009）：库内无参考商品。”

名称有多个可能、规格冲突、库内已有商品但缺图，以及系统连接失败，均须按各自实际情况说明，不能笼统归为库内无商品。名称是简称但能唯一对应时，不因名称未逐字一致列问题。
