# 核销资料分块检索与结构化核对

本实现接在原资料上传、解析、分类和核销链中，不增加上传端口、业务类型、接口参数或模型平台。检索范围只有本次运行，使用资料角色、本单核销号及精确关联申请行，不使用向量数据库、相似度 Top-K、其他核销结果或跨任务审核结论。

## 分块与证据完整性

1. 所有原文件、图片、POS行和勤策原始返回继续完整读取、保存。全量资料盘点独立于某一检索块；一个块未带入的资料不能被说成客户未提交。
2. 较长的总审按经销商与签章、活动日期、预算、POS、结算、付款、票据、照片等审核用途切分。每项规则的资料角色有明确依赖表；未登记的依赖回到全量来源，不用关键词猜删资料。
3. POS事实按原工作表、原行及大小切分，重复提供同文件同工作表的真实表头；范围清单检查重叠、中间缺口、末尾缺失和整份来源遗漏。局部块不能判全表合计；商品身份和全量金额复算由程序在合并后统一核对。
4. 能建立完整原生POS计划时，按准确69码建立数量索引。索引明确标记为程序派生值，不能伪造为原始单元格。模型使用 `right_group_ref` 选择对应商品组，程序展开全部原行、来源和数量后，继续原有逐字引用、原精度及比较方向校验。不能建立完整索引时不使用部分合计冒充整表。
5. 完整规则结果合并后再验证一次；规则遗漏、非POS块重复、跨块证据冲突、POS范围不全均不能被当作已完成审核。合并不再新增一次携带全包资料的总审模型调用。已确认条件不适用的整块由程序按原条件处理并明确记录未调用模型。
6. 八类分别生成 `references/stage-plan.json`，登记审核用途、每批规则、资料角色、必需参照及返工上限。模型输入输出上限均为null，不设应用层硬限制。长单按用途分块，每批最多四项，结算数值规则逐项分块；小单可合并，仍执行相同来源及字段自测，不为制造stage额外请求模型。不适用项逐项按原条件由程序处理，不再因混在适用项中而重传整包材料。
7. 当前运行已经验证的POS商品查库结果由程序生成对应检查，不再让模型复述后重新判断。完整原生复算计划仍交原数值校验器计算全部行；不能把中间占位unknown当最终通过。不跨单复用审核结论，不新增常驻或无界缓存；临时索引随本次材料规模增长，由原运行结束流程释放。

`CONTEXT_BYTES=48000` 是资料分块触发值，不是Token数。原文片段、重复元数据按可还原字典编码传递，全部行、来源及精度保持。各阶段编译自己的规则及依赖口径，不再默认发送Skill、审核表、业务指南三份全文；读图只提供资料角色范围和可见事实提取要求，资料门禁不带后续业务审核全文。

用户2026-11-09最新要求不设置模型输入输出硬上限。核销API不发送 `max_tokens` 或 `max_completion_tokens`，不因文本字节数直接拒绝调用。128000 UTF-8字节仅作为多规则分组的拆分目标，单规则完整送入；输入字节和实际Token分别记录。结算数值规则各自请求，结算公式不带无关勤策数据，申请数量/单价不带核销节点金额行。供应商真实返回容量错误时，多规则块二分重建请求，保留前序成功结果；每个子块规则数严格缩小，单规则错误仍明确失败，不接受截断JSON或无限重试。图片批处理、网络时限与流式接收安全保护沿用原机制，不是模型Token封顶。CLI继续按相同阶段和来源标准执行。

## 勤策只取、只传必要数据

对齐按字段的实际值判断：勤策有有效值时必须按本项含义核对，并以勤策为参照；空字段跳过该字段的勤策对齐，不进入客户问题摘要，不补0、不影响合同、POS等材料自身检查。数字及日期、条码精确比较，0是有效值；名称允许合理文字模糊匹配，包括线上/线下后缀和轻微写法差异。原名与原始引用保持不变，实际不同分店、数字编号及多候选歧义不能被模糊匹配吞掉。数值校验器禁止在勤策已有有效标准时改用合同另一个值自证通过；计划销量与实际销量仍先区分含义。

- 保留本单核销查询、精确关联申请查询；只有本单申请从方案继承商品时才查对应方案。不新增接口参数或臆造服务器字段过滤能力。
- 补充主档按明确用途登记，不对所有类型默认查商品或终端。人员激励、POS达标激励、物料制作不查询勤策终端和商品主档；POS商品身份继续使用项目配置的商品数据库，费用代垫经销商、周期及申请金额沿用关联申请实际字段，不另查主档。陈列堆头为认店和估算尺寸查询对应终端、商品及包装尺寸；条码费、搭赠、外采赠品和补差仅保留照片认店辅助的终端查询。未知类型/未指定用途不执行补充主档查询。识别码接口没有已确认的服务端商品筛选参数时，响应后仅投影本单关联商品，不能声称远端已只返回单个SKU。
- 默认不查询历史识别/校对报告、原始识别、比对结果、铺货实绩及标准等历史辅助接口。已有离线技术快照仍能只读解析，但不因此在正常运行恢复整套查询。
- 模型不接收部门、负责人、联系人电话、无关标签、客户启用/审批状态、商品图片URL等管理字段。核销审批状态仍保留，避免把审批中节点金额当最终批复；两种状态含义不能混淆。
- 名称与签章只带经销商参照；日期只带活动周期；金额只带相应总额、批复及审批含义；照片只带本单店名/位置、活动周期、商品及约定规格，不带行预算和经销商比较字段。地址是辅助，不要求水印逐字完整。
- 相同字段值按本单用途共享，保留所有不同值和代表来源；全部原始行及来源关系仍由程序校验和技术档案持有。不得把删掉重复传输理解为删掉真实行、门店、商品或源资料。

用户2026-11-09进一步明确：以上是辅助取数范围，不代表这些字段全部必须与核销材料对齐。客户摘要只呈现实际材料问题，辅助取数限制仅留技术档案。`available_reference:<rule_id>:<原条件>` 由程序结合当前来源状态和原业务分支编译；辅助参照不存在时不新增该项系统字段对齐，已取得但模型漏用时必须返工。照片、水印、付款截图自身日期、POS和原始资料的检查继续独立执行，不能把它们的真实问题覆盖成“本检查未引用申请字段”。

| 场景 | 勤策补充主档 | 使用边界 |
|---|---|---|
| 人员激励 | 不查终端、商品主档 | 申请中已有的经销商、周期及确有用途的约定可辅助；销售提成实际销量与完整POS核对，不强制与计划销量相等；不要求审批先完成 |
| POS达标激励 | 不查终端、商品主档 | 奖励标准取本次真实规则，实际销售额取POS，商品身份取项目商品库 |
| KT板等物料制作 | 不查终端、商品主档 | 制作数量、单价、金额及前后照片依据本次材料，不为内部复算额外查询主档 |
| 补差 | 仅照片认店辅助终端 | 价格、日期及全部POS原值各自核对，不把辅助地址缺失变成问题 |
| 搭赠 | 仅照片/小票认店辅助终端 | 规则及活动范围来自本单材料及实际关联明细，原商品身份沿用项目商品库 |
| 外采赠品 | 仅活动现场认店辅助终端 | 实物、现场及采购/制作原始凭据独立核对，不额外查勤策商品主档 |
| 条码费 | 仅上架照片认店辅助终端 | 实际SKU以协议/本单活动范围及商品库核对，原渠道、照片比例和库存要求不变 |
| 陈列堆头 | 对应终端、商品及包装尺寸 | 仅辅助认店和尺寸估算，不证明实际已执行；全部照片仍独立分析 |

金额来源：真实申请总额优先；没有该字段时，`qince_amount_basis.py` 证明本次核销行与申请行的完整关联、去重、客户身份及金额有效性，按Decimal精度求和。数值比较展开为全部原申请行操作数，再由既有计算器核验，禁止用计算结果伪造原文。部分行、串单、重复冲突不能组成合计。有效批复仅实际取得时比较，审批前未形成的最终金额不作为资料缺失；这不把当前节点金额伪称最终审批通过。

## 输入字段合同

正式定义为 `contracts/audit-reference-input.schema.json`，由 `audit_core.audit_rag.REFERENCE_INPUT_SCHEMA` 生成。每个字段保留原始 `source_fields`、原值和全部不同值对应的来源ID；不能以行金额填充整单金额，也不能用核销申报替代申请。

| 核对字段 | 允许来源及原字段 | 边界 |
|---|---|---|
| 费用代垫经销商 | 本单关联申请的 `dealerName/dealerCode/dealerId`、已有 `advanceDealerName` 或对应自定义列 | 客户名称、终端名称、核销实际代垫名称不能自动替代申请经销商 |
| 活动周期 | 本单申请 `startDate/endDate`，或保留原申请行关联的进场记录 | 签约、签章、付款、提交日期不能替代活动周期 |
| 申请数量、申请单价 | 本单申请 `quantity/unitPrice`、数量和单价自定义列 | 空值、未返回及已取得但未完成核对分别处理；不自动按预算反算 |
| 申请商品 | 本单关联申请 `pdCodes/pdNames/pdIds/barcode` 及活动SKU、条形码自定义列 | 保留名称、编码各自实际字段；不以客户名称补商品 |
| 整单申请总金额 | 独立申请主档 `applyAmount/totalAmount/budgetAmount` 或明确的申请总金额列 | 申请行 `applyAmount` 不当作整单总额 |
| 最终核销批复合计 | 独立核销批复来源中的明确合计字段 | 申报金额、预算、任意审批节点金额不当作最终批复合计 |

状态区分 `missing`（未取得该字段）、`empty`（返回空值）、`incomplete`（端点或部分来源不完整）、`invalid`（不能解析）、`available`（同一可用值）、`multiple`（多个不同值）。`multiple` 不自动等于冲突。字段已取得不表示审核通过。

## 输出 Schema 与程序核对

- 实际模型请求按块生成 Schema，限定本块 `rule_id`、来源ID及专用证据对象。程序的输入字段合同要求完整状态盘点；模型的 `reference_reads` 和 `reference_evidence` 是可兼容的辅助输出，旧有效回答不因没有新增辅助字段而整单失败。已返回的辅助项仍须使用真实状态、完整不同值及对应来源，不能把已有值说成未取得；缺少回执会在分块记录中如实显示，不编造“模型已经读过”。原有来源、角色、引用、数值及业务审核继续执行。
- 经销商项的 `reference_evidence` 分别保留填写名称和落章名称的 `unit_id/quote/value`；原文必须来自对应业务资料，名称逐字存在于引用中，落章证据不能用公司抬头替代。程序按实际申请名称精确比较，错字和漏字仍报告。
- 活动周期项保留对应合同或结算单的全部周期原文。程序核对日期与申请；另一页不同期间不得省略。支持“日”“号”的日期写法，叙述“在此活动期间临时聘请促销员”不能被当作一个缺少起止日期的新字段。
- 已取得字段但尚未完成关联引用，保留为未完成核对，不能归咎于客户没交申请资料。原始模型响应仍保存，不修改其原文；程序核对结果与客户摘要按既有执行链生成。
- 初次读图可返回 `field_inventory`，明确每张资料的填写经销商、落章名称及活动周期是否可见，以 `fact_indexes` 引用本张原事实，避免再次复制长段文字。逐张覆盖及事实索引在有该辅助输出时校验；未返回辅助盘点不新增整单失败门禁，不补造可见内容。对应合同为 `contracts/visible-field-inventory.schema.json`。

## 客户总结与输出长度

`reason` 直接给客户阅读，一两句说哪个对象有什么问题，不复述接口字段、候选排除、规则和已通过的日期。完整原文、逐行计算和逐图证据在对应字段与技术档案保存。通常通过项建议120字以内，问题或无法确认项建议480字以内；Schema使用描述引导，不以 `maxLength` 把较长但有效的回答变成执行失败。程序合并分块时保留所有真实问题，不为满足长度而截断后半部分。

门店名称在本单范围内大体相近、核心商号一致且没有明确不同分店或地点事实时可以接受，不要求逐字同名、详细地址或额外别名/一一映射证明。已可近似对应就不列问题；确实无法认店时简短说明，例如“照片里的甲店，暂时对不上本次活动门店名单。”。存在具体分店、地点或编号冲突时保留真实问题，条码、金额、数量、单价及日期不作模糊比较。

已由原生同行乘法公式、原始因子及二进制运算精确证明的缓存表示差异，可以按文件合并说明，并保留一个原值例子；所有行、原值、公式、比较结果及严格状态不改变，不引入金额容差。文字金额、无法证明的公式和实际金额不足继续逐项报告。此处是摘要表达去重，不是财务审核豁免。

## 唯一自测门禁与定向返工

用户已选择自测，不另建重复评测链。`contracts/stage-self-check.schema.json` 是实际执行报告：阶段rule_id无遗漏/重复/越界、所需字段状态和来源、原文/角色与原精度计算校验、确定的漏读及明显病句检查。自测由程序完成，模型调用0。它不能证明所有中文都自然、所有图都识别准确。

已有可用字段却说“未取得”、已有申请行金额/审批状态却说金额“均未取得”、通过或不符结论未用有效参照、重复词及明显程序式病句，会触发当前阶段的定向返工。总审继承的有效逐图来源计入自测，不因总审占位字段为空重复拦截。

每阶段至多新增一次返工调用，每次只尝试一次；只传待修条目及本单对应来源。纯措辞返工只返回reason补丁，不再重传全表；程序保留原状态、数值、比较、来源，不允许新增数字或日期。返工后代码复测，通过才进入下一阶段；仍不通过保留原响应和 `stage_rework_pending` 断点，不能冒充审核完成。真实未交、确实模糊、真实缺字段或冲突按原业务规则正常输出，不强制编造通过。

`audit_tools.py --case <本单保存的case.json> <tool>` 与模型受限 `tool_requests` 复用七个代码工具：`reference_fields`、`linked_application_amounts`、`pos_calculation`、`source_inventory`、`activity_periods`、`pos_field_inventory`、`pos_matrix_identity`。仅当前单、当前阶段及字段白名单，只读且无网络、任意命令、SQL或跨单读取。代码可先执行已知工具；模型需要补查时返回闭合Schema，程序执行真实结果后交回同阶段一次补审。申请行合计只标注其真实范围，不能冒充主档总额或最终批复；全量POS展开证明继续保存。

横向POS矩阵先按本文件、本Sheet内相邻名称/69码原列头读取商品身份，继续原商品库核对。全部门店销量行仍留原事实，由同列绑定证明其身份范围，不能每店重复转录或从别表补商品。明确多级合计表头按原列位置关联，不由价格猜SKU。未能完整证明时沿用原模型读取，不新增失败或缺件。各阶段只展示当前用途的工具说明，照片阶段不预读POS矩阵、预算工具；这只缩短提示，不拒绝旧合同允许的已保存响应。

长单POS的5+2字段已由`pos_field_inventory`完整证明时，沿用程序生成的`pos_fields`，不再为该项把全表分块交给模型。证明必须覆盖全部原生来源、各文件各Sheet独立表头、每条明细、实际活动时间及两项合计，保留表头、时间、范围和合计位置；只索引原行，不在内存复制整表解析单元格。时间可来自本表活动标题、明确期间表头或日期列（含起止分列）；月日简写只证明字段已提供，不补年或代替严格的期间对齐。程序无法完整证明时仍使用原模型阶段，不据此报客户缺件或整单失败；商品身份查库和精确算术继续独立执行。

## 验证边界

`tests/test_audit_rag_contract.py` 覆盖字段状态、跨单隔离、准确来源引用、真实日期与名称差异、全量POS分块、程序数量索引展开及规则合并。保存的实际核销资料可离线重建检索包并比较文本字节，但这不等于调用真实模型重跑，也不能当作真实Token账单降幅。客户Key、服务器发布和旧单回调仍按各自授权范围执行。

分块主要降低单次输入/输出过长的风险；本阶段完整规则在对应system中，必要原图仍有费用，请求次数也可能增加。局部文本、索引引用或摘要变短不保证整单账单按同比例下降。真实用量必须在取得当次授权后，以各次真实请求返回的计量汇总，不能把字节当Token或将未知记0。

设计参考用户指定仓库的 [阶段自测](https://github.com/yzzzzzzz123/codex_agent_product_info_template_pro/blob/main/skills/taojin_v3_crawl_skill/scripts/stage2_self_test.py) 和 [字段锚点](https://github.com/yzzzzzzz123/codex_agent_product_info_template_pro/blob/main/skills/taojin_v3_crawl_skill/references/stage2_anchor_schema.md)：采用固定阶段产物、字段来源锚点、代码检查与有界返工，不移植其SPU/SKU业务规则、浮点价格容差或额外评测流程。
