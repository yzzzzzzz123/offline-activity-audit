# 额外搭赠核销

涉及商品知识时，先读取[数据库知识规则](../../shared/product-database/audit-knowledge.md)，统一通过
`audit_core.product_database.load_product_catalog` 查询数据库；需要参考图片时，只按数据库的 `image_manifest_key` 从私有 OSS 取图；不存在本地图库入口或回退。
沿用本场景原有业务证据链，数据源调整不额外增加商品主账检查条件。

生成客户错误原因和处理方式前，必须读取并执行[统一文案规范](../orchestrate-offline-audit/references/error-reasons.md)。
错误原因只写具体错误事实，建议只写处理方式；涉及的业务文件区域只列相关实际文件 basename；回调只保留原因。核销类型由 ZIP 名称的唯一已登记标记确定，AI 不得改类。ZIP 名称无法唯一分类时由编排器直接打回，不调用本 Skill 或 AI；已知类型的错件、缺件及内部文件误命名仍继续审核或材料诊断。

将一项 `giveaway_promotion` 申报作为独立的额外搭赠报销链核销。压缩包标记 `额外搭赠` 或
`搭赠` 可以路由结构相容的全视觉材料包，但必须由合同和结算单的可见内容确认申报确实针对
额外赠品。

提取或判断任何案例前，必须完整读取 [audit-rules.md](references/audit-rules.md)。可见事实阶段
必须符合 [evidence.schema.json](references/evidence.schema.json)。规范化设计合同及代表性 ZIP
来源位于 [scenario-manifest.json](references/scenario-manifest.json)。

## 证据链

必备证据链为：

1. 一份由经销商签署的促销合同，明确符合条件的购买商品、赠品、购赠比例、活动期间、赠品预算
   和报销证据；
2. 一份经销商盖章的公司结算单，分别标明正常发货金额、额外赠品申报、分项赠品数量、单位
   价值和计算过程；
3. 一份系统销售/发货明细，证明结算单采用的正常发货行及合计；
4. 一张或多张合同期内门店小票，每张都独立显示符合条件的付费商品和满足合同比例的零价值
   赠品行；
5. 一张或多张活动期照片，证明门店、参与商品及额外搭赠执行。

由于相机导出文件名可能没有业务含义，所有已提交视觉文件首先绑定到中性接入角色
`visual_document`。AI 只读取可见标题和事实；随后由确定性验证要求每个来源恰好出现一次，
并唯一绑定合同、结算单、系统明细、小票、照片、支持资料或其他可见文档类型。单例业务角色
重复会形成需要继续材料诊断的歧义。缺失角色则作为正式结果中的分组阻断问题保留。

## 信任边界

- AI 只读取隔离的已提交图片或 PDF 渲染页并返回可见事实。它绝不核准报销、执行算术、读取
  `input/` 或历史输出，也不从另一来源复制数值。
- 确定性 Python 验证来源覆盖和角色基数，核对哈希、相关方、期间、商品对应、小票比例、零
  价值赠品、发货合计、赠品计划计算、上限、结论、结果 Schema 和发布。
- 正常销售/发货金额只是上下文，不是额外赠品申报。合计一致不能替代缺失的合同、结算明细、
  小票、活动照片、赠品数量或单位价值。
- 商品名称是唯一模糊辅助证据。可比来源均印有产品编码或 69 码时，这些标识符必须严格一致。

## 输出合同

内部六列工作簿投影保留问题来源、观察、规则、结论、金额影响和操作。单一自包含 HTML 的
`额外搭赠核销` 逐项显示具体错误原因，并在独立处理方式中显示对应操作；结论、影响和识别过程不混入两栏。

申报金额来自经销商盖章结算单的额外赠品金额，绝不能取正常发货金额。只有全部阻断控制通过，
且分项赠品计算与已签署合同预算、盖章结算申报均精确到人民币 0.01 元一致时，才支持全部申报；
否则支持金额为零，并暂缓全部申报。

只能通过父级命令运行：

```powershell
py -3 skills/orchestrate-offline-audit/scripts/run.py --run-id <YYYYMMDD-id> --producer-model <executor> --scenario giveaway_promotion
```
