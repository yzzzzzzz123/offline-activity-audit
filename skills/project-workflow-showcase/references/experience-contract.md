# 展示页体验契约

创建一份编辑式技术解读：对工程师而言信息足够密集，对决策者而言顺序足够清楚，并明显针对项目自身领域设计。
读者应留下“我理解这个系统如何运行”的印象，而不是“我看过一个仪表盘”。

## 信息架构

使用最小且连贯的故事，通常包括：

1. **固定方向标识：** 项目名称、简洁描述和本地导航。
2. **首屏：** 一句话目标、运行边界，以及真正有助于读者定位且由源码推导的标题事实。
3. **架构：** 一张说明职责或层级关系的图。
4. **工作流：** 一张展示正常顺序和主要门槛的图。
5. **深入说明：** 根据证据需要说明项目专属组件、契约、接口、状态、恢复、文件和验证。
6. **结尾边界：** 系统保证什么、拒绝什么，以及哪些留给人工或外部服务。

不得强加固定章节数、阶段数、角色名称或统计数字。导航标签应简短，并使用读者的语言。

## 视觉语言

- 选择一个与领域紧密相关的鲜明方向：核销项目可以使用精确的证据台账风格；创意工具可以使用工作室或目录风格。避免通用紫白色 AI 仪表盘。
- 使用字体、留白、节奏、克制配色、边框粗细及一个令人记住的结构母题建立层级。
- 优先使用少量大型说明组合，不要铺满统一卡片网格。
- 盒子与流程优先使用 HTML/CSS 图示；只有关系会明显更清楚时才使用内联 SVG。应可选择或可访问的文字不得做成图片。
- 使用语义标签区分职责类型、门槛、存储、外部系统和人工决定。任何颜色编码都必须有图例说明。
- 代码片段保持简短且有明确目的。使用文件树或职责图，不要粘贴大段源码。
- 动画只用于方向或状态变化，并遵守 `prefers-reduced-motion`。

## 交互与无障碍

- 本地导航使用真实锚点。使用页签时，应设置页签角色、`aria-selected`、键盘方向键导航，并提供无 JavaScript 时安全显示的第一个视图。
- 每个按钮必须有明确 `type`、无障碍名称、可见焦点状态和有效行为。不得把看似禁用的装饰渲染为控件。
- 保持语义标题顺序和地标结构。文字无法直接说明关系时增加 `aria-label`。
- 保持足够对比度，绝不能只依赖颜色传递信息。
- 宽度约 390 px 时，将复杂网格改为纵向排列，允许局部表格/代码块滚动，并保持文档本身无横向溢出。

## 自包含实现

- 使用一个 UTF-8 HTML 文件，包含内联 `<style>` 和可选的内联 `<script>`。
- 不得使用外部字体、图标、图片、样式表、脚本、API 请求、iframe、service worker 或分析调用。
- 优先使用文字、CSS 图形、克制的 Unicode，以及带无障碍标题的内联 SVG。确需位图时，只能以 data URI 嵌入。
- 保持来源路径为相对路径，避免机器、账号、租户、令牌及真实业务记录细节。

## 参考比较

用户提供参考页面时，只有根据项目证据生成页面后才能比较。评估：

- 首屏是否同样清楚地说明目标和系统结构？
- 阅读者能否在架构、工作流及实现细节间移动而不丢失上下文？
- 技术密度是否通过图示、标签和渐进深度得到组织？
- 当前项目的独特边界是否比参考来源的视觉习惯更明显？
- 新页面是否为独立设计，且没有复制业务语言、标识符、固定指标、DOM 骨架或 CSS token 系统？

## 浏览器验收

以约 1440×960 的桌面视口及约 390×844 的移动端视口测试真实最终文件。
验证所有可见控件、哈希导航、焦点、控制台输出、离线加载及横向溢出。
至少截取首屏/架构视图和工作流视图。页面较长时，必须检查首屏以外的内容。
