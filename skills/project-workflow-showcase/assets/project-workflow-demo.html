04 / OSS

三字段入站，完整任务生命周期。

外部系统只发送 verifyCode、analyzeId、downloadUrl；签名查询串只在内存中使用。

UPSTREAM

业务系统

在受信任内网提交一个 ZIP 对象；verifyCode:analyzeId 形成稳定业务身份，终态重投会覆盖上游最新结果。

accepted
验证请求合同三个字段完整、回调已配置、同一身份未指向另一对象；运行中重复合并，终态重复创建新尝试。
downloading
安全下载并验 ZIPHTTPS 443、精确域名白名单、公网解析、大小、ETag / SHA-256 与 ZIP 格式。
downloaded
进入串行核销队列ZIP 已校验落盘且签名 URL 已丢弃；下载 worker 可继续处理后续 ZIP。
running
调用唯一正式 runner单核销 worker 严格串行执行 bundled run.py，并读取原子结果收据。
callback
构建三字段回调回传相同 verifyCode、analyzeId 与来自正式快照的两句式中文 result：分析概况一句，错误原因一句。
completed
保存完成事实传输重试只重发已保存结果；上游再次提交才新建尝试、重跑 AI，旧档案不覆盖。
CALLBACK

只回结论

POST /api/v1/ai/analyze/callback
不回传下载地址、本地绝对路径或密钥。

失败如何留痕？
下载或核销失败写入任务 failure，并在 OSS 投递区显示“失败”和安全原因；核销已经完成但回调失败时保留正式 worktree、原始 ZIP 与结果收据，并标记 callback_failed。失败不混入核销台账，底层记录仍留在技术档案；服务重启会把未完成入站任务安全终止为失败，不伪装为完成。
连续投递如何展示和取消？
一级页面逐条显示全部未完成或失败 attempt：接收、下载和已落盘等待统一标为“排队中”，正式核销和回调标为“运行中”，失败标为“失败”。三类卡片都有“删除记录”；同源确认后，排队项从 worker 跳过，运行项先终止专属 runner 并阻止尚未发出的回调，再清理唯一归属的收据、ZIP 与未完成档案。系统总览直接展示全部状态的核销台账，技术档案使用相同记录集合。

DETERMINISTIC CODE

代码核对来源、复算金额、执行匹配规则并形成统一结果对象。

  • 统一结果包含 summary 与 exceptions

IDENTITY

ATOMIC
先验证，再原子写入

08 / GUARD

失败关闭，不靠“应该没事”。

每个外部边界都有可执行拒绝条件；异常不会用旧结果、拼接结果或无证据结论替代。

ZIP / 01

压缩包先过安全门

拒绝路径穿越、盘符、链接、加密成员、重复目标和异常压缩比；限制 2,000 个成员、单成员 250 MiB、总展开 1 GiB。

OSS / 02

临时链接不成为档案

只允许 HTTPS 443 和精确白名单域名；签名 URL 不写入任务收据、日志、worktree 或回调，错误信息再次脱敏。

OUTPUT / 03

未验证页面不能发布

证据 Schema、统一结果 Schema、内部六列投影和最终 HTML 依次通过校验；临时文件在结束路径统一清理。

DELETE / 04

不可逆动作必须精确授权

普通运行删除只允许终态记录；OSS 排队、运行和失败任务走专用 job 路由。两者都要求同源 Origin、进程 nonce 和完全匹配的目标 ID；链接、共享分支或归属歧义一律拒绝。
