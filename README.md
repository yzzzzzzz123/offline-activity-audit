# 线下活动核销

本项目把一至十份活动材料 ZIP 生成可审计的持久化运行档案，并统一展示在根目录唯一版本化页面 [`offline-activity-audit.html`](offline-activity-audit.html) 中。页面由本地可信服务持续提供，可在本机或受信局域网打开；每个运行目录还会生成同源的离线静态档案。系统支持十类材料：

- 人员激励：销售 Excel、结算单图片、转账或红包截图；
- 堆头陈列：销售 Excel、合同 PDF、现场照片；
- 海报/物料制作：签章促销合同、发票或收据、客户盖章结算单、现场水印返图。
- 其他费用：无法归入现有费用类型的新费用、独立特殊审批、签章促销合同、公司统一模板且有客户盖章的结算单，以及按新类型提供的协议/相关文件/活动照片/POS等。
- 维护费用：经销商盖章POS数据、对应POS电子表、具体费用协议/相关文件/活动期照片、公司统一模板且经销商盖章的结算单，以及签章促销合同；这是独立场景，不是直营，也不替代其他费用。
- 额外搭赠：经销商签章促销合同、经销商盖章结算、系统销售/出货明细、活动期内门店小票和活动照片；正常出货金额与额外赠品申报金额分开核对。
- 价格补差：经销商盖章POS、对应电子表、公司统一模板盖章结算单、签章促销合同，以及覆盖全部活动门店且带日期/地址/时间水印并清楚展示活动价的现场照片；合同补差单价独立于终端零售价差额。
- POS达标激励（经销商）：盖章逐门店POS及电子表、战略/批准特殊渠道与档位比例明确的签章合同、满减活动水印照片/小票/其他存在证明，以及按最高达标档位和上限计算的统一模板盖章结算单。
- 进场费/条码费：双方签章进场费合同/产品推广协议、覆盖合同商品和合同门店的水印上架照片，以及合同要求的系统扣款凭证；条码费按合同商品行合计，未明确按店计费时不再乘门店数。
- 客户自采赠品物料：签章促销合同、费用明细和开具时间清晰的发票/收据、清楚的赠送规则、经销商盖章POS及独立POS电子表、覆盖全部活动门店并显示日期/地址/拍摄时间/促销内容/自采赠品的水印照片，以及公司统一模板客户盖章结算单。

可以只提交其中一类，也可以多类各提交一份。核销方式由 ZIP 名称唯一确定后，客户漏交、多交、业务文件误命名或同类多包时，正式 runner 会继续 AI 材料诊断：读取可用图片/PDF，区分单据用途和分页，再报告缺少哪些材料、哪些文件完全重复或存在角色冲突、哪些内容尚不能确认。缺失项只按该类要求列出。ZIP 名称没有或同时包含多个类型标记时直接退回，不调用 AI；原因只说明名称未标明核销方式或包含多个核销方式，改名重交仅写在处理方式。混合批次只退回这些包，其余已分类包照常处理。

文件名含 `物料` 自动归入海报/物料制作；没有具体类型标记但含 `费用` 时自动归入维护费用。具体类型优先：`费用申请.zip` 为维护费用，`物料制作费用.zip` 为物料制作，`其他费用.zip` 和 `自采赠品物料.zip` 保留各自专门类型。多个具体类型冲突仍退回。input 导入和 OSS 接收使用同一规则。

材料诊断完成后会生成正常的持久结果页与中文摘要，并通过原有 OSS 回调返回全部具体缺口及相关文件名；完成分析不表示核销通过，也不会产生虚构的通过检查或支持金额。不安全 ZIP、下载失败、模型执行故障及非法证据仍以运行失败结束。API `1.38` 的 `/api/config.material_problem_policy` 为 `analyze_and_report`。


核销类型是开始业务核验的前提。ZIP 名称未注明类型或包含多个具体类型时，该包核销失败，不调用 AI；运行 manifest、snapshot、正式收据及 OSS job 均为 `failed`，失败代码为 `classification_failed`，不发布 `run.completed`。CLI 以退出码 2 返回已保存的失败收据，OSS 仍按原三字段契约回传 `核销失败：核销方式无法确认` 及全部具体原因；回传成功只表示送达，不能把核销改成完成。回传失败单独记为 `callback_failed`，原核销失败与原因继续保留。混合批次中已知类型照常检查并保留结果，只要仍有无法分类的包，整次记录为失败。类型已确定且业务核验执行完成后，材料缺失、金额差异等才作为完成结果中的失败检查项展示，与正确检查项并列。旧档案若曾把分类退回标成 completed，工作台只读投影为失败，不重写历史证据或自动重发回调。

## 使用方法

商品名称、编码与69码统一读取 MySQL；参考图片已迁往私有 OSS
`offline-verify/product-reference/<product_code>/`，数据库 `image_manifest_key` 指向多视图清单。
AI 只接收按需下载并校验的临时图片，任务结束清理；不持久化签名链接，不使用旧索引文字。
部署、凭据与迁移操作见 [商品数据库与 OSS 说明](shared/product-database/README.md)。

1. 把一至十个原始 ZIP 直接放入 [`input/`](input/README.md)，不要手工解压。
2. 启动固定工作台服务；服务监听全部本机网卡，当前页面地址为 `http://192.0.0.148:8080/`：

```powershell
py -3 -B skills/orchestrate-offline-audit/scripts/serve.py --host 0.0.0.0 --port 8080
```

直接双击根 HTML 会跳转到已配置的本机工作台地址；同一局域网内的设备使用服务启动时输出的
`lan` 地址。

3. 在项目根目录运行唯一正式核销入口：

```powershell
py -3 skills/orchestrate-offline-audit/scripts/run.py --run-id 20260817-simple-001 --producer-model codex
```

只需要其中一种结果时追加 `--scenario personnel_incentive`、`--scenario promotional_display`、`--scenario poster_material`、`--scenario other_expense`、`--scenario maintenance_fee`、`--scenario giveaway_promotion`、`--scenario price_difference_support`、`--scenario pos_target_incentive`、`--scenario entry_fee` 或 `--scenario self_procured_gift_material`。例如本次仅核销海报/物料制作：

```powershell
py -3 skills/orchestrate-offline-audit/scripts/run.py --run-id 20260827-poster-material --producer-model codex --scenario poster_material
```

视觉提取默认固定使用 `gpt-6-astra`，并隔离本机 Codex 的插件、Hook 和其他个人配置，避免正式运行受本机配置漂移影响。Windows 会在独立安装的 Codex CLI 与桌面版内置 CLI 中选择最近更新的版本，并为每次运行加载该 CLI 的临时内置模型目录，避免全局 CLI、在线刷新和本机模型缓存之间的版本冲突。运行前必须确认所选 CLI 的内置模型目录包含 `gpt-6-astra`；可通过 `OFFLINE_AUDIT_MODEL` 替换为当前 CLI 内置的其他模型，或通过 `OFFLINE_AUDIT_CODEX` 显式指定兼容的 CLI 文件。商品候选预检只提取现场可见锚点，固定使用 `medium` 推理；合同、人员材料和最终现场图—参考图联合判断默认同样使用 `medium` 推理。用户于 2026-09-10 选定常规运行配置为 `gpt6astra_medium`；OSS 子进程显式传入该模型和档位，避免环境变量使实际配置漂移。正式入口会逐阶段打印实际耗时；超时和传输类失败可按上限重试，非法 Schema、无效请求、认证/权限或模型配置错误立即失败关闭，不重复提交同一无效请求。

如模型连接需要单独代理，可在启动工作台服务或正式 runner 的进程环境中显式设置 `OFFLINE_AUDIT_MODEL_PROXY`，值为包含主机的 HTTP/HTTPS 代理 URL，例如 `http://127.0.0.1:7897`（端口应以本机实际配置为准）。它只覆盖模型子进程的 HTTP、HTTPS 和 ALL_PROXY 大小写变量，不修改全局环境，也不改变 OSS 下载或回调连接；`NO_PROXY` 保持继承。未配置或空值继续继承原环境，不自动探测或选择端口。代理地址及其中凭证不会加入命令行、提示词或运行日志；无效地址按配置错误停止。

## OSS 自动投递、状态查询与可选回调

一次 OSS 请求对应一份 ZIP 和一次正式核销运行。上游只提交 `verifyCode`、`analyzeId`、
`downloadUrl` 三个业务字段。单个下载 worker 按接收顺序尽快下载并校验 ZIP，持久保存到
`input-oss/<job_id>/<原始文件名>.zip`；下载与前一任务的正式核销、回调并行，不需要等待 AI 完成。
单个核销 worker 再严格串行地把每个已下载任务目录作为 `--input-dir` 调用唯一正式 `run.py`，
因此不会并发运行多个视觉模型任务。默认模式在分析完成并原子保存 worktree 后，额外生成
`worktrees/<workspace-id>/ai-analysis-summary.md`；该文件是给业务部门阅读的排版化 AI 小结：仅按场景分节并逐条列具体错误原因，保留定位问题所需的业务文件 basename、缺失字段和必要差值；仅合并完全相同的原因，不合并不同对象的同类错误，不截断。小结不包含场景/错误总数、运行元数据、置信度或补交建议。随后向上游的 `POST /api/v1/ai/analyze/callback` 回传同一个
`verifyCode`、`analyzeId`，并将这份 Markdown 小结作为中文 `result`。
材料诊断的小结保留每项缺失材料，以及每组重复文件/角色冲突的全部原始文件路径；相同错误类型合并不能丢失不同文件组。
显式启用 `--oss-no-callback`（或 `OFFLINE_AUDIT_OSS_NO_CALLBACK=1`）时，服务接收并处理
相同三字段请求，但不发送结果回调；调用方通过任务状态接口查询完成状态。
显式启用 `--oss-receive-only`（或 `OFFLINE_AUDIT_OSS_RECEIVE_ONLY=1`）时，服务只下载、
校验并持久保存 ZIP，不启动正式核销，也不发送结果回调。

同一 `verifyCode:analyzeId` 在当前尝试仍为 `accepted`、`downloading`、`downloaded`、`running` 或 `callback`
时只返回该任务，不会并发重复分析；当最近一次尝试已经 `completed` 或 `failed` 后，同一对象
路径再次投递会创建新的尝试号、任务号、独立 `input-oss` 目录和 worktree，重新下载并运行 AI。
新回调仍携带原 `verifyCode` 与 `analyzeId`，因此上游可用最新 `result` 覆盖业务结果；本项目不覆盖
或删除旧输入、旧任务收据和旧 worktree，仍保留完整审计历史。

启动前配置 OSS 下载域名白名单和完整回调地址。入站接口不要求鉴权，只应暴露在受信任的
内部局域网，不得直接开放到公网：

```powershell
$env:OFFLINE_AUDIT_OSS_CALLBACK_URL = "https://业务系统.example/api/v1/ai/analyze/callback"
# 如果业务回调接口要求 Bearer Token，再设置这一项：
$env:OFFLINE_AUDIT_OSS_CALLBACK_TOKEN = "请替换为回调密钥"

py -3 -B skills/orchestrate-offline-audit/scripts/serve.py `
  --host 0.0.0.0 `
  --port 8080 `
  --enable-oss-intake `
  --oss-allowed-host audit-materials.oss-cn-hangzhou.aliyuncs.com
```

`OFFLINE_AUDIT_OSS_CALLBACK_URL` 默认必须是完整 HTTPS 地址，且路径固定为
`/api/v1/ai/analyze/callback`；只有相对路径还不足以发送回调。也可以用
`--oss-callback-url` 传入。受信任局域网内的业务接口若只有 HTTP，必须同时显式设置
`OFFLINE_AUDIT_OSS_ALLOW_HTTP_CALLBACK=1` 或追加 `--oss-allow-http-callback`，且不得把该
例外用于公网。`OFFLINE_AUDIT_OSS_ALLOWED_HOSTS` 可用逗号分隔多个精确下载
域名；下载上限、下载超时、回调超时和回调次数分别由
`OFFLINE_AUDIT_OSS_MAX_BYTES`、`OFFLINE_AUDIT_OSS_DOWNLOAD_TIMEOUT`、
`OFFLINE_AUDIT_OSS_CALLBACK_TIMEOUT`、`OFFLINE_AUDIT_OSS_CALLBACK_ATTEMPTS` 调整。
OSS 下载使用独立直连连接，不读取 `HTTP_PROXY`、`HTTPS_PROXY` 或 Windows 系统代理；
白名单、HTTPS/TLS 校验及每次重定向校验仍然生效。结果回调也使用自己的独立直连连接；模型和系统代理配置不变。API `1.38` 的 `oss_intake.callback_transport` 为 `direct`。
下载连接错误区分拒绝连接、超时、连接重置、域名解析和 TLS 失败，诊断消息不包含签名 URL 或底层异常原文。
下载失败的 attempt 不自动重试；上游使用新的有效签名链接重新提交相同业务二元组及对象路径，创建下一次 attempt。
仅在调用方明确不接收结果回调时，启动参数追加 `--oss-no-callback`，此时可不配置
`OFFLINE_AUDIT_OSS_CALLBACK_URL`；不要静默省略回调并冒充默认正式模式。
若当前阶段只收集原始 ZIP，改用 `--oss-receive-only`；任务状态在下载校验完成后直接变为
`completed`，`delivery.input_file` 给出 `input-oss/<job_id>/` 下的持久文件位置。

上游向本项目提交：

```http
POST /api/intake/oss HTTP/1.1
Content-Type: application/json; charset=utf-8

{
  "verifyCode": "HX202603250014",
  "analyzeId": 123,
  "downloadUrl": "https://白名单OSS域名/维护费用.zip?临时签名"
}
```

默认模式正式分析完成后，本项目向配置的业务系统回调：

```http
POST /api/v1/ai/analyze/callback HTTP/1.1
Content-Type: application/json; charset=utf-8
Idempotency-Key: HX202603250014:123:<result-sha256-16>

{
  "verifyCode": "HX202603250014",
  "analyzeId": 123,
  "result": "# AI 小结\n\n## 维护费用核销\n\n- **POS电子表缺失**：未提交可读取的POS电子表。\n- **合同盖章缺失**：合同未显示有效盖章。"
}
```

- `verifyCode:analyzeId` 是稳定业务身份。同一对象路径在最新尝试运行中重复投递只返回原任务；最新尝试终态后重复投递会生成 `attempt=2/3/...` 的新任务并重新分析。响应中的 `rerun=true` 表示本次已创建覆盖业务结果的新尝试，`supersedes_job_id` 指向上一尝试；同一组合改投另一个对象路径仍返回 `409`。
- `downloadUrl` 必须是白名单域名的 HTTPS 443 地址。临时签名查询串只保存在内存，不进入任务收据、日志、worktree 或结果回调。
- 下载响应或 URL 路径应保留 Windows 安全的原始 `.zip` 文件名及业务场景标记。服务记录响应 ETag、实际字节数和自行计算的 SHA-256，并验证文件确实为 ZIP；残缺或无效下载会删除。
- `verifyCode` 中首个有效 `YYYYMMDD` 用作运行业务日期；没有有效日期时按上海时区收件当天生成。`analyzeId` 必须是 64 位正整数。
- API `1.25` 将接收、回调及任务状态中的 `fileId` 更名为 `analyzeId`；旧参数请求返回 `400` 更名提示。历史回执只读映射为 `analyzeId`，原有身份指纹和重投链保持兼容，不重写旧回执或重发历史回调。
- `result` 直接读取正式 worktree 根目录的 `ai-analysis-summary.md`，不由 HTTP handler 另做业务分析；内容按场景标题和错误项目符号排版，完整保留各对象的具体错误原因，文件仅用 basename，不重复错误标题或附加说明。它不包含 `downloadUrl`、本地绝对路径、密钥、总数概况、完整证据长文、运行元数据、置信度或补交建议，也不得以“另有 N 项”省略错误类型。
- 回调以 `2xx` 为成功；`Idempotency-Key` 由 `verifyCode:analyzeId` 和三字段回调正文摘要组成，使不同分析结果可更新上游、同一结果的传输重试仍可去重。网络错误、`408`、`429` 和 `5xx` 按配置有限重试；重试只重新投递已保存结果，绝不重新运行 AI。
- 默认模式状态依次为 `accepted → downloading → downloaded → running → callback → completed | failed`。`downloaded` 表示临时签名已不再需要、ZIP 已安全落盘并等待单个核销 worker；下载 worker 可继续接收后续 ZIP。显式无回调模式跳过 `callback`，任务完成后将回调状态记为 `not_required`；只接收模式为 `accepted → downloading → completed | failed`，不创建核销 worktree。分析成功但默认模式回调失败时，任务记录为 `callback_failed`，已完成的 worktree 和原始 ZIP 仍然保留。
- 状态查询为无需鉴权的 `GET /api/intake/jobs/<job_id>`；API `1.38` 的一级工作台轮询 `GET /api/intake/jobs?completed=0`，只展示尚未完成及失败的 OSS attempt：`accepted/downloading/downloaded` 统一显示为“排队中”，`running/callback` 显示为“运行中”，`failed` 显示为“失败”并保留失败原因。为不中断升级时正在处理的真实任务，页面在旧 API `1.19` 服务尚未安全重启时会回退读取完整列表并在本地排除 `completed`。完成的 attempt 不再占用投递区，其正式完成运行只进入“最近核销记录”和仅含完成记录的核销台账。`GET /api/intake/jobs?active=1` 仍可用于只读活动任务检查。任务收据位于隐藏的 `worktrees/.intake/jobs/`。
- 投递区的排队、运行和失败卡片始终提供“删除记录”。同源确认的 `DELETE /api/intake/jobs/<job_id>` 会让排队任务从 worker 队列跳过；运行任务先取消专属正式 runner、阻止尚未发出的回调，再删除该 attempt 的收据、`input-oss/<job_id>/` 和唯一未完成 worktree；失败任务则删除其收据、ZIP 和唯一关联运行档案（如有）。已经发出的业务回调不能撤回。完成记录及非 OSS 失败记录仍通过原运行删除接口处理。

本地 `input` 运行只生成报告，因为它没有 OSS 请求中的上游业务身份。需要向客户交付一份已完成报告时，使用补发工具，显式指定正确的 workspace 和业务二元组：

```powershell
py -3 -B skills/orchestrate-offline-audit/scripts/deliver_callback.py --workspace-id <workspace-id> --verify-code <verifyCode> --analyze-id <analyzeId>
# 核对预览后，以相同参数增加 --apply 投递；使用既有 OFFLINE_AUDIT_OSS_CALLBACK_* 环境配置。
```

## 主流程任务清单

正式运行固定执行以下六项主流程任务，运行档案、只读 API 和首页运行链共用同一份顺序与文案：

- [ ] `01 bootstrap` — 运行初始化：建立持久化运行目录；
- [ ] `02 intake` — 材料分流：识别场景与资料角色；
- [ ] `03 analysis` — AI 识别：提取材料中的可见事实；
- [ ] `04 evidence` — 证据校验：核对 Schema 与来源边界；
- [ ] `05 decision` — 核销决策：执行确定性业务规则；
- [ ] `06 verification` — 结果封存：验证页面投影与技术档案。

主流程任务清单由 `audit_core.workbench_store.main_flow_task_list` 统一提供，并写入每个新运行的
`manifest.json`；页面不得再维护另一套不同名称或顺序的六阶段定义。多场景运行按 stage 成批
推进：先完成全部场景的 AI 识别，再统一做全部证据校验，再统一执行全部核销决策，最后封存；
不得再按单个场景交错产生 `analysis → evidence → decision → analysis` 的倒退事件序列。

成功后会建立一个持久化运行目录，并从根目录唯一版本化前端原子生成该次运行的独立静态页面：

```text
worktrees/<压缩包名>-<YYYYMMDD_HHMM_SS>/
├─ offline-activity-audit.html
├─ manifest.json
├─ snapshot.json
├─ logs/events.jsonl
├─ logs/run.log
├─ analysis/
└─ dom/checkpoints/
```

`--producer-model` 保留执行来源信息，例如 `codex`；`--model` 和 `--reasoning-effort` 记录
本次实际模型与主要推理强度，也可分别由 `OFFLINE_AUDIT_MODEL` 和
`OFFLINE_AUDIT_REASONING_EFFORT` 提供。`--run-id` 必须以有效的 `YYYYMMDD` 业务日期开头，
但该日期只保留为业务元数据。`worktrees/<压缩包名（去除 .zip）>-<YYYYMMDD_HHMM_SS>/`

新目录按本次实际核销压缩包命名，保留中文和可用标点；文件系统不允许的字符替换为下划线，过长名称只在目录部分截短，完整源文件名保存在 manifest 的 `source_archives`。一次多包核销使用首个包名及包数；指定单一场景时由既有安全分类器选择其对应包。时间后缀使用上海时区的运行预留时间，同名同秒重复核销追加 `-02`、`-03` 等唯一后缀，禁止覆盖。
模型及推理强度保存在元数据并显示为小标签，例如 `gpt6astra_max`，不再写入新的资料目录名。`run-id` 的业务日期仍保留为业务元数据，不用于展示分析日期。旧目录、旧 ID 和既有静态档案不批量改名或重写；目录 API 从已保存材料分类与启动事件只读补全压缩包标题、来源和分析日期。无可用材料名称的初始化失败仍保留旧格式安全目录作为回退。
原有历史 HTML 与旧命名目录继续保留，并在固定工作台中按只读兼容结果展示。新运行不再发布
Excel，也不发布运行期临时拼装页；只发布上述与局域网二级页同源、同视觉、只读且自包含的静态
档案。直接双击运行目录内的页面即可离线查看该次核销结果、分析文件、DOM 断点与日志。

## 处理边界

AI 只负责读取视觉材料中的可见事实：

- 人员激励读取结算单和转账截图；
- 堆头陈列读取合同和现场照片；
- 海报/物料制作读取合同、票据、结算单和每张现场水印返图；POS 等无关材料不进入视觉核销。
- 其他费用读取所有已绑定的促销合同、结算单、支持协议/文件、活动照片、POS、票据和特殊审批候选；AI只提取可见事实，确定性代码先判断是否能归入现有类型，再核对新增类型审批和资料完整性。

海报/物料制作按“签章合同 → 发票/收据 → 客户盖章结算单 → 水印成品照片”闭环。合同引用的门店清单等附件必须同时提交；合同有多类物料时，票据只写笼统的“物料制作”不能替代名称、数量、单价和小计。现场返图必须落在合同周期内，逐张核验日期、拍摄时间和地点，并共同证明成品内容、尺寸、摆放位置及合同数量/门店覆盖；错误原因仅显示其中未通过的具体事实。默认错误总览只列影响核销的错误、涉及文件和补交动作；已独立确认通过的子检查在同页“正确检查项”日志中查看。

其他费用不是兜底分类。系统先用资料中的具体费用描述排除赠品、陈列堆头、人员激励、海报/物料制作、维护费用、补差、搭赠、POS达标激励和进场费；能归入现有类型时，结果逐文件写明应归类型并要求重新分类或拆分。确实无法归类的新费用必须提交独立特殊审批，明确新增类型、审批主体、批准意见、日期和审批完成标记。即使审批和资料齐全，系统也不自动建议核销金额：保留结算单申报金额，自动建议金额为0，交由有权审批人核定。

额外搭赠按“签章促销合同 → 经销商盖章结算 → 系统销售/出货明细 → 门店小票 → 活动照片”闭环。系统把正常出货金额与赠品申报金额分开；逐张小票核对活动期、合格购买商品、零金额赠品和合同买赠比例，不跨小票拼凑比例。赠品金额只按合同明确的数量和单价或完整逐项小计复算，并同时受合同预算和盖章结算申报约束。小票不能替代合同要求的活动现场照片；任一阻断项失败时全额暂缓。

正式商品身份主账统一为 MySQL `product_catalog.products`，由
`audit_core.product_database.load_product_catalog` 使用 TLS 只读账号查询。
所有核销 Skill 遵循[数据库知识规则](shared/product-database/audit-knowledge.md)：
人员及合同商品核对只用数据库名称、编码、69码；堆头按同一现场照片文字从数据库召回候选，
随后只按数据库 `image_manifest_key` 从私有 OSS 读取多视图清单及所选参考图片，并验证 SHA-256。
旧 JSON 中的名称、别名和观察文字不再提供分析知识。当前数据库未登记的编码别名不能用于放行。
同次核销共用一致快照，记录到 `analysis/product-database.json`；下一次运行重新查库。
数据库故障、空表或数据非法直接报告系统失败，不回退历史 JSON。其他场景原有业务证据链保持不变。

数据库自检：`py -3 -B -m audit_core.product_database`。部署与迁移见
[商品数据库说明](shared/product-database/README.md)。后文“商品知识库/目录”均指数据库快照，
“参考图/图片清单”指数据库关联的 OSS 资料，不指任何本地目录。

GitHub 的 `shared/canban-product-multimodal-knowledge-base/` 原目录仅是独立灾备：保留远端内容，
不作为依赖、不检出到本地工作目录、不参与候选匹配或测试。数据库或 OSS 故障直接报错，不能自动启用此备份。
灾备恢复必须另行授权；先恢复到数据库和 OSS 并验证，再继续正式核销。运行副本使用 Git sparse-checkout 排除此目录，
该本机检出设置不删除远端文件。发布提交时必须核对该目录 Git tree 未发生变化。

人员激励场景也先经过正式商品知识库。确定性代码按69码汇总销售 Excel 后，要求69码是
有效 EAN-13 且与知识库精确一致，再只在该69码的候选商品内用原始产品名做唯一模糊
兼容匹配；名称逐字相同只是最高分特例，不是通过条件。人员销售表没有产品编码列，因此产品编码由知识库匹配结果提供，不反向写回或
改写 Excel。69码无效/未登记、产品名明显冲突或同码多商品无法唯一消歧时，该商品暂不
进入支持金额；商品参考图不发送给人员结算单识别，也不作为结算或转账证据。
结算单未显示条码时，若某个结算数量只对应一个尚未使用且已通过知识库核验的 Excel SKU，
代码会在“一行一条码”约束下直接建立中置信度映射；结算单商品名只作模糊辅助，OCR 缩写、
错字或残缺不会推翻这个唯一数量映射。数量重复且名称也不能唯一消歧时才保留为未确认。

堆头场景以合同 PDF 为业务核销主文件，先逐项核清合同签订方、活动预算金额、执行周期、
活动内容、核销方式和盖章；合同水印只作信息记录，不参与核销状态、金额或补交判断。经只读查询、结构及69码校验的数据库商品主账
只负责商品身份：合同核心条款明确限定的商品、以及合同附加销售明细中的每一行商品先对照
知识库一次：有效69码必须精确命中知识库，业务文件的本地商品编码既在合同附件与销售
Excel之间精确核对，也必须精确命中数据库的 `product_code`；当前表没有编码别名，
旧 JSON 别名不能替代数据库登记。商品名称只作规格兼容的模糊
辅助，不要求逐字一致，也不再单独产生“商品名称：不匹配”错误；严格标识和独立交易字段已
唯一定位时，名称未识别也只作辅助信息，不影响结论、问题数或补件。产品编码和69码共同命中后
仍对应多个知识库商品时，用合同PDF中可见的商品名称做唯一模糊消歧；若首轮OCR把实际有文字的名称格识别为空，
必须回看原分辨率单元格，不能误报为产品编码问题。`SP-1` 等包装短码可在
商品描述及数据库名称/准确编码中同时出现时作为名称模糊匹配锚点，但不能替代合同、附件或销售文件中的正式商品编码。
聚焦复读会先从同一 PDF 扫描页生成四个方向并选出两张横向阅读候选，再生成重叠行带；红章
跨过表格时，额外从同一 RGB 像素分离黑色印刷层、裁出产品编码/名称/69码列并放大。模型只采用
文字朝上的一组，沿同一行从数量、价格、金额定位产品编码、商品名称和69码格，并对照彩色原带与黑字带，
不能把红章笔画、旋转 OCR、相邻行或 Excel 值当作合同原文。

现场商品身份独立判断：先逐张提取现场照片真正可见的名称片段、短码、规格、香型/款式、
组合装文字等，再只用这些照片文字从完整有效知识库中召回少量候选，最后把现场包装与候选
参考图做视觉比对。照片不要求拍到完整名称或69码；数据库名称或编码中实际存在的唯一文字，或能唯一收敛
的名称片段/规格/款式文字，只要与知识库文字对应且包装关键特征大体一致，就可判定“现场商品
知识库”一致。例如 `3+2`、`420g`、`量贩装`可组合召回知识库中的3+2量贩装商品；现场图与
多方位参考图的主体色块、版式和组合结构相容且没有冲突即可，不要求拍摄角度、距离、光线、
遮挡或包装姿态完全相同。仍有多个候选时保持待核验，不能拿合同或销售 Excel 帮助识别。商品身份确定后，再单独
判断它是否属于合同范围，因此“现场商品知识库”通过不等于“现场商品与合同”必然通过。
参考图只证明商品身份，不能证明门店、日期、陈列、促销或照片未复用。
商品与门店完整识别后，系统会只拿已绑定的现场照片再做一次陈列标准聚焦复核，并且只覆盖
陈列观察，不重做商品、门店、日期或促销结论。“4纵陈列”按同一实体堆头上从左到右同时
可见、可独立分辨的实体商品列计数：三个正面礼盒加上第三个礼盒自身露出的窄侧板仍是三列，
不能把一个包装的两个表面重复计数；三列正面商品之外若另有一组边界独立、连续堆放的包装，
即使透视压窄或略呈侧面，也算第四列。不同参半 SKU、组合装和包装形式可以共同组成四列，
不要求四列都是同一商品，但不能把相邻其他品牌算入。一个门店有多张照片时逐张判断，任一单图
独立证明四列即可通过，不能跨照片拼加零散列数。三列正面礼盒旁一排贴合窄侧面仍按三列，除非
包装接缝、错位或独立正面能证明另有实体堆叠。上下堆叠、重复货架层、背景货架或完全被遮挡的
推测列不得累加。

对已由用户验收并写入永久交付标准的视觉边界样本，Skill 还维护一份透明的 SHA-256 回归校准表。
只有合同门店与有序照片哈希同时逐项完全相同时才应用确认过的陈列观察；照片改动一个字节、增删或
调换照片、变更门店路由都会自动失配，继续使用本次新视觉判断。命中的校准 ID 会写进提取备注，
相似图片或同名新图片不能复用旧结论。

海报/物料数量覆盖采用同一安全边界，但按完整有序返图集合绑定：只有全部文件名与原始字节
SHA-256 逐项一致，才复用用户已验收的物料可计数总量和涉及照片数。改图、改名、增删或调序都会
失配；数量校准不能改写水印、地点、日期、尺寸、合同、票据、结算单或金额，也不会进入客户页面。
对已经人工逐份核实、但视觉读取容易波动的永久标准单据金额，另以“合同 + 票据 + 结算单”的完整
有序文件名和原始字节 SHA-256 集合绑定，只允许回填表内明确声明的三项金额。任一文件改动、改名、
增删或调序都会失配；该机制不能修复主体、日期、明细、盖章、附件、照片或其他项目事实。

合同门店与水印地点文字完全对应时直接通过，不产生地点问题，也无需调用地图。只要两处文字
不同，系统就调用百度地图 MCP 查询双方候选并给出地点置信度：同一 POI、商场与店内门店的
父子关系，或选定 POI 的直线距离不超过 100 米，均为“高置信度”并通过。搜索结果不必各自
唯一；可信唯一的一侧保持不变，所有尚未唯一定位侧只要存在名称相关性达到 0.60 内部门槛、且
能够与另一侧形成上述同址或临近关系的候选，就采用该配对；双方均不唯一时两侧候选都须达到
门槛。相距较远、100 至 300 米灰区、没有可信候选配对、坐标不可比或 MCP
不可用，才属于“低置信度／待人工核验”，暂不自动核销，但不自动定性为“门店水印错误”。
相距较远时，台账明确保留距离依据，并要求补充同址/临近证明或重新提交正确地点照片。台账同时
保留是否调用 MCP、提供方、选定 POI/地址、BD09LL 坐标、距离、阈值、置信度和判定依据；客户
页面不展示内部相关性分数。水印地点确实缺失或无法识别仍是独立证据缺口，照片文件名不能证明
或覆盖地点。

正式地点解析只使用百度地图官方 Streamable HTTP MCP 固定端点
`https://mcp.map.baidu.com/mcp`，并调用 `map_search_places`。应在百度地图开放平台创建服务端
AK，并开启所需服务。AK 配置名固定为 `BAIDU_MAPS_API_KEY`：程序优先读取当前进程环境，
Windows 上未设置时自动读取当前用户的系统环境配置（`HKCU\Environment`），因此一次写入本机
用户配置后，后续可直接运行核销命令，不需要另开终端再次输入。AK 不写入项目文件、Git、日志、
结果 JSON 或核销台账；程序会先进行 URL 编码，再作为 `ak` 查询参数发给固定官方端点，也不
输出含 AK 的完整请求 URL。需要更新或删除时，应在 Windows“编辑账户的环境变量”中操作
`BAIDU_MAPS_API_KEY`，不要把真实值写进 `.env`、脚本或命令行参数。

AK 若启用 IP 白名单，应填写“实际运行核销服务进程”的公网出口 IP：本地测试时填当前电脑所在
网络的公网出口 IP，不填 `127.0.0.1`、`192.168.x.x`、`10.x.x.x` 等本地/内网地址；宽带重拨、
更换 Wi-Fi、VPN 或代理后公网出口可能变化，需要同步更新白名单。正式部署时填写服务器或其
NAT 网关的固定公网出口 IP。可用 `OFFLINE_AUDIT_LOCATION_MCP_TIMEOUT_SECONDS` 设置 5 至
120 秒超时。MCP 未配置或候选配对仍无结论时，系统才查阅
`skills/audit-promotional-display/references/location-resolution-registry.json`；该表必须通过
同目录 Schema，且每条映射至少保留两项可回查来源。当前“挺拇指生活超市（横沥店）—东莞市·
南铭购物乐园”已按公开门店地址及东莞市市场监督管理局同址材料登记为商场与店内门店关系；
“润家连锁超市（美联购物中心店）—深圳紫云快捷宾馆”的既有静态映射保留登记时取得的两地点
65.4 米历史地图证据，二者均为高置信度。该历史证据不会改变新的在线提供方；所有新在线查询
固定走百度地图 MCP。若百度地图 MCP 与已复核映射冲突，始终降为低置信度并转人工核验，不
自动通过或判错。

合同 PDF 末尾若附有销售明细，视觉模型会把它单独转录为合同附件明细，逐行保留客户、
业务日期、商品编码、商品名称、69码、单位、数量、零售价、合计金额和来源页；看不清的值
保留为空，不会心算补齐。附件印刷的总数量、总金额只在原页明确出现时抄录，不从明细求和。
附件表不是合同核心条款：它不会变成核心合同限定商品，也不会变成促销要求，但它仍属于合同
主文件，是销售 Excel 逐行核销的唯一基准。没有附件时，销售 Excel 没有合同逐行基准，
结论为“无法核对并补交完整合同附件”，不能改用知识库或现场照片替代。

堆头核销按相互独立的证据链闭环：合同商品 → 商品知识库；现场照片文字 → 完整有效知识库的
少量候选 → 候选参考图视觉比对，再将已确认的现场商品单独对照合同范围；
销售 Excel → 合同附加销售明细。最后一段逐行核验客户名称、业务日期、商品编码、商品名称、
条形码、数量、零售价和合计金额，并复核合同附件与 Excel 各自的行内金额和打印总计；双方
单位仍保留并展示，但不参与配对、通过结论、置信度或补件要求。销售 Excel 不再对知识库，
现场照片也不与销售 Excel 核对。合同附件与销售
Excel 都没有权威门店列，不能分摊到某一家门店或冒充单店销售证据。合同只有明确的按店或按
堆头单价时才自动计算；只有总额或口径不清时不做平均分摊，转人工确认。

销售 Excel 不提供给 AI。Excel 单元格读取、商品映射、数量汇总、金额复算、日期/地点/重复检查、核销结论、客户视图投影和运行快照发布均由确定性 Python 完成。

每次运行只使用本次 ZIP。业务判断不会读取历史结果、缓存或验收工作簿；解压目录、临时工作簿、模型工作区和临时投影会在结束时删除。人工原包仍由 `input/` 管理，OSS 已验证原包按任务保存在 `input-oss/`；只有本次运行的结构化证据、确定性结果、验证收据、可观察日志和 DOM 数据断点进入自己的持久化 worktree。

断电、崩溃或强制关闭进程留下的临时材料和 OSS 参考图，会在**下次正式核销启动时**自动补清理，无须定时守护。
`audit_core.run_temporary` 在系统临时目录创建 `oa-<worktrees范围摘要>-<随机标识>/`，
只有 `data/` 存放本次临时文件；外层归属登记和操作系统占用锁不提供给模型。
新任务只清理同一范围、登记有效、占用锁已释放且没有子进程引用的目录，不按年龄或 PID 判断失效。
链接、归属不明、权限不足或文件占用会跳过并保留待重试；清理日志只报告目录数量，不暴露图片、凭据或进程命令行。
未登记的旧版临时目录不能仅凭名称自动删除。原始 `input/`、`input-oss/`、正式 worktree、数据库备份和 OSS 原图不受影响。
对用户已明确确认归属及中断状态的单个旧临时目录，可由维护操作调用
`register_abandoned_legacy_temporary`：先验证实际系统临时路径、全部子项无链接且没有进程引用，
再同卷移入带登记的临时容器，图片不在迁移时删除，由下一次正式启动补清理；普通启动不会自动接管旧目录。

## 输出内容

根目录的 `offline-activity-audit.html` 是唯一版本化前端和局域网入口。它不会被普通核销运行
改写，页面通过本地可信服务读取 `worktrees/` 中的原子快照。服务不依赖公网、CDN、远程字体
或第三方脚本；局域网客户端通过同一相对 API 查看一级核销系统和任意历史二级记录。每个运行
目录另有一份从该根页面原子派生的同名静态档案，只包含当前记录并可脱离 HTTP 服务查看。
运行过程中仍会在系统临时目录生成用于确定性整理和校验的工作簿及旧版页面投影，但两者都
不会发布，并会在成功或失败后删除。

台账与技术档案共用 `/api/runs` 中全部 worktree 记录的顺序、搜索条件和可见窗口，包含运行中、失败、已完成状态；二级记录切换器使用同一集合。概览的总记录数、顶部及侧栏计数统计同一全量集合，搜索不改变总数。概览“运行中的记录”合并活动 OSS attempt 与未关联活动 attempt 的运行中 worktree，按 `run_id` 去重，并用“OSS 上传”或“input 导入”标签标明来源。“最近核销记录”只展示 `completed` 和 `failed` 终态记录；没有五条上限，按每批 100 条显式继续显示。三个列表共享搜索和可见窗口状态，台账与技术档案始终保持成员及顺序相同。无 worktree 的失败投递单独显示在“投递失败”区。新建、完成、失败、人工核验和删除通过同一目录修订刷新；陈旧响应不得恢复已删除记录。API `1.38` 的 `refresh_policy` 声明这些规则，历史静态 HTML 不自动重写。 记录标题使用去掉 .zip 的压缩包名称，完整文件名仍可搜索；模型及强度以 `gpt6astra_max` 等小标签与来源、场景标签并列。新 API 直接提供只读标签；旧 API `1.19` 仅对当前窗口及活动记录按最多四并发读取已有 `002-intake` 小型检查点，缓存名称，避免下载完整业务快照。

所有运行卡、技术档案及二级记录标题的日期采用 AI 首次开始分析时间 `analysis_started_at`，统一按 `Asia/Shanghai` 显示；旧档案缺失此字段时回退到 `created_at`，绝不使用材料业务日期替代。新运行将首个 `scenario.started` 事件时间保存为分析开始时间，后续场景不得覆盖。来源优先使用明确的来源标记或关联 OSS 任务，历史内置 OSS 运行可按保留的 `YYYYMMDD-oss-<12位十六进制 job 前缀>` 身份识别，其余直接输入显示为 input 导入。状态文字始终保留：运行中用琥珀色，失败用红色，完成用绿色；技术档案卡的色条、状态徽标和抽屉状态使用相同规则。

  运行中的记录、未创建 worktree 的失败投递和最近终态记录，不展示核销运行链路、阶段节点或运行事件。首页只静默探测轻量运行目录，并在
  运行目录签名变化时更新可见内容，不再为首页读取所选运行快照。运行中的二级页仍只在 stage

## 新增核销场景

新增业务不是把一段提示词直接塞进现有视觉模型，也不是只复制一个 `skills/audit-*` 目录。
当你提供一份具有代表性的新 ZIP 和一段业务核销规则时，使用
[`create-offline-audit-scenario`](skills/create-offline-audit-scenario/SKILL.md)：

```text
使用 $create-offline-audit-scenario。
样例 ZIP：D:\codex\offline-activity-audit\input\<新场景>.zip
业务规则：<权威材料、必核字段、金额口径、通过/待补条件、输出要求>
```

生成器先安全盘点 ZIP 的文件角色和嵌套结构，再把业务提示规范化为场景 manifest，创建独立
场景 Skill，并一次性接入 ZIP 路由、视觉事实提取、确定性核销、结果 Schema、六列表中间层、
同一 HTML 的场景界面、`--scenario` 参数和自动化测试。只有完整链路和真实样例验证全部通过
后，新场景才会被激活；正式运行仍只有原来的 `run.py` 一个入口。

先判断“新 ZIP 是否只是已有场景的新案例”。客户、月份、活动编号或文件名变化不会产生新
Skill；只有材料角色、权威证据链、确定性规则或输出对象确实不同才创建新场景。当前
`SQ202512250099-HX202601060019-展示道具.zip` 已属于 `poster_material`，不会再次生成第四个
重复场景。

旧材料诊断的客户投影必须遵循唯一 ZIP 名分类：名称唯一明确且与已保存场景一致时，不再将旧 `scenario_unconfirmed` 当作客户错误；仅在内存副本排除该条，原始结果和证据保留。缺件、不可读、实际金额差异及角色关系问题继续显示。分类错误按明确诊断代码归为费用类型，不因正文含金额词而归到金额复算。
