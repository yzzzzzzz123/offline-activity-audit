# 线下活动核销

本项目把一至两份活动材料 ZIP 从零生成一份可直接打开、自包含的参半活动核销 HTML。支持两类材料：

- 人员激励：销售 Excel、结算单图片、转账或红包截图；
- 堆头陈列：销售 Excel、合同 PDF、现场照片。

可以只提交其中一类，也可以两类各提交一份。同类重复、类型不明、材料缺失或 ZIP 不安全时，程序会停止并给出明确原因。

## 使用方法

1. 把一至两个原始 ZIP 直接放入 [`input/`](input/README.md)，不要手工解压。
2. 在项目根目录运行唯一正式入口：

```powershell
py -3 skills/orchestrate-offline-audit/scripts/run.py --run-id 20260817-simple-001 --producer-model codex
```

视觉提取默认固定使用 `gpt-5.6-sol`，并隔离本机 Codex 的插件、Hook 和其他个人配置，避免正式运行受本机配置漂移影响。Windows 会优先使用当前 Codex 桌面版自带的 CLI，并为每次运行加载该 CLI 的临时内置模型目录，避免全局 CLI、在线刷新和本机模型缓存之间的版本冲突。可通过 `OFFLINE_AUDIT_MODEL` 替换为当前 CLI 内置的其他模型，或通过 `OFFLINE_AUDIT_CODEX` 显式指定 CLI 文件。商品候选预检只提取现场可见锚点，固定使用 `medium` 推理；合同、人员材料和最终现场图—参考图联合判断继续使用 `high` 推理。正式入口会逐阶段打印实际耗时；超时和传输类失败可按上限重试，非法 Schema、无效请求、认证/权限或模型配置错误立即失败关闭，不重复提交同一无效请求。

成功后只生成一个正式文件：

```text
worktrees/<YYYYMMDD>-<producer-model>.html
```

`--producer-model` 标注实际执行本次任务的模型：Codex 使用 `codex`，其他模型使用如
`qwen3.7` 的明确标签。`--run-id` 必须以有效的 `YYYYMMDD` 业务日期开头；后面的
追踪标识不会进入最终文件名。首次 Codex 结果例如 `20260818-codex.html`。同日期、
同模型再次生成（包括同一输入重跑）时不会覆盖，而会依次生成
`20260818-codex-1.1.html`、`20260818-codex-1.2.html`。不同模型分别计数；历史版本
被移走或删除后也不会回填空缺编号，而是继续使用当前最高版本加一。正式运行不会在
`worktrees/` 发布 Excel、JSON、图片目录或第二个页面。

## 处理边界

AI 只负责读取视觉材料中的可见事实：

- 人员激励读取结算单和转账截图；
- 堆头陈列读取合同和现场照片。

人员激励场景也先经过正式商品知识库。确定性代码按69码汇总销售 Excel 后，要求69码是
有效 EAN-13 且与知识库精确一致，再只在该69码的候选商品内用原始产品名做精确或唯一
模糊匹配。人员销售表没有产品编码列，因此产品编码由知识库匹配结果提供，不反向写回或
改写 Excel。69码无效/未登记、产品名明显冲突或同码多商品无法唯一消歧时，该商品暂不
进入支持金额；商品参考图不发送给人员结算单识别，也不作为结算或转账证据。

堆头场景把仓库内经过结构、69码和图片哈希校验的商品多模态知识库作为商品身份的权威
核销账本。确定性代码读取并保留销售 Excel 每一行的商品编码、商品名称和69码；合同明确
限定具体商品时，也把合同商品映射到知识库；现场照片通过多视图检索和逐面比对先取得
知识库商品，再从该商品的69码精确值和商品名称模糊对应关系重新定位销售行，确认销售行
独立指向同一知识库商品后逐字段核对。商品名称都允许模糊对应，不要求逐字相同；销售行的商品
编码（含已登记别名）和有效69码必须与知识库严格一致。现场照片不要求拍到完整名称或69码，
看清像 `SP-1` 这样在知识库中唯一的商品短码即可确定商品；确定商品后，程序再用该知识库
商品登记的69码与销售 Excel 比较。短码只用于现场照片确定知识库商品，不能在销售商品名称里
直接定位销售行，更不能覆盖另一商品的名称或69码。找不到69码精确且名称可对应的有效销售行时，
只要求重新导出该商品的正确销售明细，不把其他商品行改写成现场商品。现场商品还只能模糊判断时，69码写“暂时不能判断”，
不会因为照片没拍到条码就误写成“不一致”。未登记的外部商品编码仍会判错。
参考图只证明商品身份，不能证明门店、日期、陈列、促销或照片未复用。

合同 PDF 末尾若附有销售明细，视觉模型会把它单独转录为合同附件明细，逐行保留客户、
业务日期、商品编码、商品名称、69码、单位、数量、零售价、合计金额和来源页；看不清的值
保留为空，不会心算补齐。附件印刷的总数量、总金额只在原页明确出现时抄录，不从明细求和。
附件表不是合同核心条款：它不会变成合同限定商品，也不会变成促销要求。没有附件时，相关
核对为条件性不适用，不影响其他证据链。

堆头商品按四条关系闭环：现场照片 → 商品知识库、商品知识库 → 合同附件明细（有附件时）、
商品知识库 → 单独提交的销售 Excel、合同附件明细 → 销售 Excel（有附件时）。最后一条只
比较双方真正提供的客户、日期、商品、数量、价格和金额，不补造缺失字段。合同附件与销售
Excel 都没有权威门店列，因此只能证明客户活动期内的商品销售情况，不能分摊到百佳华松岗店
等某一家门店，也不能冒充该门店的销售证据。门店、日期、陈列和促销仍由合同核心条款与现场
照片证明。未被某家门店现场商品定位到的销售问题行不会连带判错该门店。合同只有明确的按店
或按堆头单价时才自动计算；只有总额或口径不清时不做平均分摊，转人工确认。

销售 Excel 不提供给 AI。Excel 单元格读取、商品映射、数量汇总、金额复算、日期/地点/重复检查、核销结论和正式 HTML 生成均由确定性 Python 完成。

每次运行只使用本次 ZIP。程序不会读取历史结果、缓存或验收工作簿，也不会留下解压目录或中间运行目录。

## 输出内容

正式交付只有这一份 HTML。它把已验证的核销事实、结论和交互全部放在同一个 UTF-8 文件
里，双击即可打开，不需要服务、网络、字体下载、同名 Excel 或额外资源目录。运行过程中可
在临时目录生成用于确定性整理和校验的工作簿，但不会发布，并会在成功或失败后删除。

一个文件内包含三个层级：

- 主界面：显示本次核销的总体结论、场景入口、通过/待补数量、金额和需要重新提交的材料；
- 人员激励子界面：逐商品显示销售 Excel、商品知识库、结算单和转账证据，把合计、实际申请
  金额、收款人/门店对应关系和完整日期集中放在“结算与付款”区；
- 堆头子界面：把活动核心合同、合同销售附件、商品对应、门店现场核验和活动结算分开。核心
  合同与最终结算不会混进门店列表；合同没有销售附件时，不显示空的附件明细表。

人员激励仍按“销售 Excel → 商品知识库 → 结算单 → 转账”逐商品核验。69码必须与知识库
严格一致，产品名可唯一模糊对应；名称没有逐字相同时只降低到中置信度，不会在数量、奖励和
身份均通过时无故要求补拍。

堆头场景把现场、知识库、合同附件和销售 Excel 的商品放在逐商品结构中核对。现场照片先
确定知识库商品；知识库再分别核对合同附件和销售 Excel；附件与 Excel 最后按各自原始行核对。
每行会写清来源页或 Excel 行、原始商品字段、哪些字段一致、哪些字段需要重交。多个现场商品
一商品一行，不压成长句。商品编码与69码严格核对，名称允许唯一模糊对应。附件与 Excel 都
没有权威门店列，页面不会把它们伪装成某家门店的销售；门店事实仍只来自合同核心条款和现场
照片。

每个商品或关系只显示一个“置信度：高/中/低”，并用人话说明需重交的 PDF 页、附件行、
Excel 行/字段、结算行、转账截图或现场照片内容。页面不会要求客户另看 JSON，也不会展示
候选命中、RAG、商品 ID、哈希或长篇模型推理。

页面外观和交互来自唯一版本化模板
`skills/orchestrate-offline-audit/assets/canban-audit-shell.html`。正式运行只能调用仓库自带的
`skills/orchestrate-offline-audit/scripts/run.py`；不要手工写 HTML、复制旧页面、运行后改
页面或另做一套前端。普通核销和普通功能修复都只注入新的业务数据，不改模板的 CSS、布局、
固定文案、交互或按钮。只有用户明确提出重新设计时，才会同步升级模板版本和校验规则。

## 安装与验证

Python 要求 `>=3.11`。项目依赖声明在 `pyproject.toml` 中。

商品参考图和权威样品 Excel 通过 Git LFS 交付。首次克隆或切换到包含知识库的版本后，必须先取得真实 LFS 对象；只有指针文件时，RAG 图片 SHA-256 校验会按设计失败关闭。

```powershell
git lfs install
git lfs pull
git lfs fsck
py -3 -m pip install -e .
py -3 -B -m unittest discover -s tests -v
```

验收用工作簿仅用于测试比对，正式运行路径和模型均不得读取它。
