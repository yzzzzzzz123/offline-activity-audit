# 线下活动核销

本项目把一至两份活动材料 ZIP 从零生成一份简明的核销 Excel，以及一份方便直接查看的本地 HTML。支持两类材料：

- 人员激励：销售 Excel、结算单图片、转账或红包截图；
- 堆头陈列：销售 Excel、合同 PDF、现场照片。

可以只提交其中一类，也可以两类各提交一份。同类重复、类型不明、材料缺失或 ZIP 不安全时，程序会停止并给出明确原因。

## 使用方法

1. 把一至两个原始 ZIP 直接放入 [`input/`](input/README.md)，不要手工解压。
2. 在项目根目录运行唯一正式入口：

```powershell
py -3 skills/orchestrate-offline-audit/scripts/run.py --run-id 20260817-simple-001 --producer-model codex
```

视觉提取默认固定使用 `gpt-5.6-sol`，并隔离本机 Codex 的插件、Hook 和其他个人配置，避免正式运行受本机配置漂移影响。Windows 会优先使用当前 Codex 桌面版自带的 CLI，并为每次运行加载该 CLI 的临时内置模型目录，避免全局 CLI、在线刷新和本机模型缓存之间的版本冲突。可通过 `OFFLINE_AUDIT_MODEL` 替换为当前 CLI 内置的其他模型，或通过 `OFFLINE_AUDIT_CODEX` 显式指定 CLI 文件。商品候选预检只提取现场可见锚点，固定使用 `medium` 推理；合同、人员材料和最终现场图—参考图联合判断继续使用 `high` 推理。正式入口会逐阶段打印实际耗时；超时和传输类失败可按上限重试，非法 Schema、无效请求、认证/权限或模型配置错误立即失败关闭，不重复提交同一无效请求。

成功后会在同一目录生成同名的两个文件：

```text
worktrees/<YYYYMMDD>-<producer-model>.xlsx
worktrees/<YYYYMMDD>-<producer-model>.html
```

`--producer-model` 标注实际执行本次任务的模型：Codex 使用 `codex`，其他模型使用如
`qwen3.7` 的明确标签。`--run-id` 必须以有效的 `YYYYMMDD` 业务日期开头；后面的
追踪标识不会进入最终文件名。首次 Codex 结果例如 `20260818-codex.xlsx`。同日期、
同模型再次生成（包括同一输入重跑）时不会覆盖，而会依次生成同名的
`20260818-codex-1.1.xlsx/.html`、`20260818-codex-1.2.xlsx/.html`。不同模型分别计数；
任一扩展名都会占用对应修订号，历史版本被移走或删除后也不会回填空缺编号，而是继续使用当前最高版本加一。

## 处理边界

AI 只负责读取视觉材料中的可见事实：

- 人员激励读取结算单和转账截图；
- 堆头陈列读取合同和现场照片。

人员激励场景也先经过正式商品知识库。确定性代码按69码汇总销售 Excel 后，要求69码是
有效 EAN-13 且与知识库精确一致，再只在该69码的候选商品内用原始产品名做精确或唯一
模糊匹配。人员销售表没有产品编码列，因此产品编码由知识库匹配结果提供，不反向写回或
改写 Excel。69码无效/未登记、产品名明显冲突或同码多商品无法唯一消歧时，该商品暂不
进入支持金额；商品参考图不发送给人员结算单识别，也不作为结算或转账证据。

堆头场景把仓库内经过结构、69码和图片哈希校验的商品多模态知识库作为商品身份的权威
核销账本。确定性代码读取并保留销售 Excel 每一行的商品编码、商品名称和69码；合同明确
限定具体商品时，也把合同商品映射到知识库；现场照片通过多视图检索和逐面比对先取得
知识库商品，再从该商品的69码精确值和商品名称模糊对应关系重新定位销售行，确认销售行
独立指向同一知识库商品后逐字段核对。商品名称都允许模糊对应，不要求逐字相同；销售行的商品
编码（含已登记别名）和有效69码必须与知识库严格一致。现场照片不要求拍到完整名称或69码，
看清像 `SP-1` 这样在知识库中唯一的商品短码即可确定商品；确定商品后，程序再用该知识库
商品登记的69码与销售 Excel 比较。短码只用于现场照片确定知识库商品，不能在销售商品名称里
直接定位销售行，更不能覆盖另一商品的名称或69码。找不到69码精确且名称可对应的有效销售行时，
只要求重新导出该商品的正确销售明细，不把其他商品行改写成现场商品。现场商品还只能模糊判断时，69码写“暂时不能判断”，
不会因为照片没拍到条码就误写成“不一致”。未登记的外部商品编码仍会判错。
参考图只证明商品身份，不能证明门店、日期、陈列、促销或照片未复用。

现场商品与相关销售行逐一对齐知识库后，堆头场景再闭合三组内部关系：合同门店/日期/
陈列/促销/可选具体商品与现场照片，现场知识库商品与销售商品编码/名称/69码，以及合同
签订方/执行期/完整性与销售客户/业务日期。未被某家门店现场商品定位到的销售问题行不会
连带判错该门店。合同只有明确的按店或按堆头单价时才自动计算；只有总额或口径不清时不
做平均分摊，转人工确认。

销售 Excel 不提供给 AI。Excel 单元格读取、商品映射、数量汇总、金额复算、日期/地点/重复检查、核销结论和工作簿生成均由确定性 Python 完成。

每次运行只使用本次 ZIP。程序不会读取历史结果、缓存或验收工作簿，也不会留下解压目录或中间运行目录。

## 输出内容

Excel 是正式六列核销表；HTML 是这份 Excel 的同内容本地查看页，不会重新判断或另算金额。
HTML 把每个工作表、每条记录和六列可见内容完整嵌入单个文件，双击即可离线打开，不需要
启动服务或联网。页面提供场景切换、关键词搜索、通过/待补/汇总筛选、紧凑显示、全部展开/
收起、复制本条结论、打开同名 Excel、打印或存 PDF、返回顶部等按钮。

本地页面按日常业务审核工具设计：顶部只保留文件与常用操作，桌面端左侧查看场景和数量，
右侧直接阅读核销记录；移动端自动改为单列。页面使用克制的浅色界面和中文无衬线字体，
不使用营销式大标题、书法字、水印、英文装饰标题、纹理或圆形记录编号。商品资料继续用小表格
呈现，文件名完整换行显示。汇总行与“通过/待补”状态分别判断，因此需要补材料的汇总项也会
出现在“只看待补”中。

- 单场景只生成对应工作表；
- 双场景固定按 `人员激励核销`、`堆头核销` 排列；
- 每张表只有六个可见列，并保留固定标题、颜色、换行、列宽、行高、冻结窗格、筛选和汇总行；
- 工作簿不含公式；
- 人员激励按“销售 Excel → 商品知识库 → 结算单 → 转账”逐商品核验，在原六列中显示
  Excel 商品、知识库产品编码/名称/69码、69码精确结果、产品名精确或模糊结果、数量、
  奖励与明确的重提要求；商品名称唯一模糊对应属于允许的中置信度匹配，只要69码、数量和
  奖励均通过，就显示“无需重新提交”，不会仅因名称没有逐字相同要求补拍；每条人员激励
  商品行直接使用已唯一确认的知识库完整商品名作为标题，不添加“结算第N行”前缀；结算单视觉识别原名保留在证据列；
- 堆头陈列固定为人类可读的六列：合同摘要、现场照片摘要、与现场商品相关的销售 Excel
  明细、合同↔现场/现场↔销售/合同↔销售三组短对比、金额计算、结论与要重新提交的材料。
  合同首行中的盖章结果固定单独占一行；合同没有明确约定具体商品或促销形式时，对应行
  直接不显示，不写“未限定”或“未要求”。现场照片先确定知识库商品，再定位销售行；
  知识库商品与对应销售行均按商品编码、商品名称、69码、数量分字段展示，不再用斜杠拼成长句；
  HTML 将同一组字段显示为紧凑键值表。所有相关销售行都在该门店行中完整展示。门店区后直接写合计
  行，不追加第二个明细区。每个商品和每组关系只显示“置信度：高/中/低”，精确、模糊或
  不匹配只放在简短的逐字段核对说明中，不再重复一个“匹配结果”总标签，并直接说明要重新提交哪份 Excel、合同或哪种现场
  照片。客户只看这一份工作簿即可；表内不会要求另看 JSON 或内部结果，也不会出现候选命中、
  RAG、商品 ID、哈希或长篇模型推理等工程表达。

## 安装与验证

Python 要求 `>=3.11`。项目依赖声明在 `pyproject.toml` 中。

商品参考图和权威样品 Excel 通过 Git LFS 交付。首次克隆或切换到包含知识库的版本后，必须先取得真实 LFS 对象；只有指针文件时，RAG 图片 SHA-256 校验会按设计失败关闭。

```powershell
git lfs install
git lfs pull
git lfs fsck
py -3 -m pip install -e .
py -3 -B -m unittest discover -s tests -v
```

验收用工作簿仅用于测试比对，正式运行路径和模型均不得读取它。
